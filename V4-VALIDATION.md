# V4 validation — levels, reputation, starboard and member profiles

## Deterministic automated checks

- `pnpm typecheck`, `pnpm test`, `pnpm build`, and `pnpm db:check` pass on the feature branch. The final regression suite includes **154 passing tests across 20 files** after the focused privacy and concurrency fixes. Existing V0–V3 tests continue to pass.
- Levels tests cover exact integer `100 × n²` XP boundaries (including terminal safe-integer XP), cooldown/duplicate eligibility, metadata fallback, unsafe reward rejection, next-level progress and SQL leaderboard ordering. Reputation tests cover valid, self/bot/young-target/member validation and internal ADMIN boundaries; a database workflow additionally verifies interaction-ID replay after cooldown. Starboard tests cover threshold crossing, repeat delivery, falling count, deletion before the first mapping commits, source message/channel deletion, NSFW/private or newly ignored sources, stale deleted events, source/destination channel changes, configuration disable/threshold changes, post-lock privacy rechecks, deleted destinations, database failure cleanup and reduced-content embeds. Profile tests cover composition and disabled source modules; dispatcher tests verify V4 commands/events are gated independently.
- These are service/dispatcher tests, **not** human Discord slash-command invocation or a substitute for cross-process PostgreSQL locking verification.

## Real PostgreSQL checks

- `pnpm db:migrate` reported **Database migrations complete** for additive `drizzle/0004_silent_the_fallen.sql` and `drizzle/0005_bumpy_forgotten_one.sql` (reputation interaction replay key), leaving V0–V3 migrations unchanged. `pnpm db:smoke` reported **PostgreSQL V0/V1/V2/V3/V4 schema, constraints and rollback smoke test passed**. The smoke driver exercises all ten V4 tables, relevant FK/unique/check constraints and transaction rollback without retaining its fixtures.
- The repeatable `pnpm db:v4` synthetic-guild driver verified all ten V4 tables and at least six applied Drizzle migration journal entries (`0000`–`0005`). Two repository instances performed concurrent increasing XP awards and preserved both, persisted cooldown across instances, checked SQL rank/top and unique reward configuration. Reputation checks verified one winner for simultaneous grants by a giver, persistent global/same-target cooldown, other-giver atomic upsert, aggregate and grant history. A replay of the exact same persisted Discord interaction ID after both cooldowns expired did not add a point/history row; changing its giver or receiver was rejected while a genuinely new interaction ID could grant again. Two starboard repository instances contended on a single source: one publication callback won, and a later instance read the persisted mapping and updated count without another source row. **All 26 `pnpm db:v4` checks passed**; the synthetic guilds and cascading V4 records were removed. Its PostgreSQL contention check held the shared source-channel reconciliation advisory lock while an ignored-channel insert attempted its exclusive lock: insertion waited until publication committed, then persisted; an exclusive destination-update barrier likewise waited for in-flight publication. All synthetic rows were removed. The applied `starboard_messages_status_check` was also verified to permit the explicit `DELETED` tombstone state.
- PostgreSQL checks do not invoke Discord members, reactions or command interactions.

## Bounded live Discord checks

- `pnpm commands:register` registered **19 guild-scoped commands** in the configured development guild. A REST readback found all seven V4 command names (`rank`, `leaderboard`, `levels`, `rep`, `reputation`, `starboard`, `profile`). A short independent bot gateway session reached ClientReady.
- In a temporary **private** text channel, the bot posted a synthetic source and reacted once. The starboard gateway counted **zero** eligible stars because the reactor was a bot, rejected the private source as a mirroring candidate, and successfully posted, updated and removed a synthetic private destination message. The temporary channel and its contents were deleted; no unrelated member was touched. This validates Discord transport and privacy filtering, **not** a positive public starboard threshold crossing.

## Still unverified

- A human-issued `/rank`, `/leaderboard`, `/profile`, configuration command or `/rep`, including a human self-rep rejection and a positive two-account grant, was **not** executed. Bot accounts cannot legitimately invoke user slash commands; no second user was available and none was awaited.
- No eligible human guild message was generated for live XP, and no positive human-star threshold crossing/removal was triggered. Command/event module gating and restart persistence were verified by deterministic and real-PostgreSQL checks, not by a human-operated restart sequence in Discord.
- Full Message Content intent is intentionally absent: short/command-like/duplicate text filtering and rich starboard text are only available when Discord actually supplies content. Metadata-only XP eligibility and reduced starboard links remain supported. No voice XP or later-roadmap achievements exist in V4.
- Reward-role assignment failures, real permission/hierarchy changes, bot network outages and human-visible notifications have not been driven in a live guild; failed role delivery is best effort after XP commit and may require staff reconciliation. Public source visibility and NSFW filtering should be checked with actual guild policy before enabling starboard broadly.
