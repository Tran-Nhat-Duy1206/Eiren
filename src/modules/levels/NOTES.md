# Levels V4

Construct `new LevelsService(new LevelsRepository(db), client, notify)` and register `levelsCommands` and `levelsEvents`; expose `levels: LevelsService` on app Services. `/rank` and `/leaderboard` are member commands; `/levels` is ADMIN. Module key is `levels`.

XP starts at level 0; level `n` begins at `100*n*n` cumulative XP (safe integer arithmetic). Each eligible message receives configured XP; crossing multiple levels grants all configured rewards in `(previousLevel, newLevel]`. `rank` sorts XP descending and user ID ascending for deterministic ties. Top 10 and rank count execute in SQL, not by loading guild members. Advisory transaction lock keyed by guild/member serializes inserts and updates across processes. Last awarded message ID, timestamp and fingerprint survive restarts; event timestamps must strictly exceed previous timestamp plus cooldown, preventing out-of-order awards. Each award persists a short truncated SHA-256 fingerprint, never content. Fingerprints only compare against the last awarded message; without a message-history table older repeated IDs/content cannot be detected indefinitely.

No privileged Message Content intent is required. When content is available, short messages, command-like messages and immediately repeated content are excluded. When content is unavailable, these checks are impossible: real-user, guild, channel, unique last-awarded ID, monotonic timestamp and cooldown checks still apply. Do not infer empty content means a short message. Voice XP is intentionally outside V4 scope.

Reward validation occurs both when configuring and immediately before assignment; unsafe, managed, internal staff, nonexistent, or uneditable roles are rejected. Discord assignment and announcement failures never roll back committed XP. Rewards are best effort; an outage after XP commit may require manual reconciliation. Routine message awards emit no guild logs to avoid spam. The optional notifier is accepted as an integration dependency but deliberately unused for routine activity.
