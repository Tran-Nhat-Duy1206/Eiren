# V8 — Approved retention and verified subject-request policy

**Status:** The V8.1 non-destructive principles remain historical evidence; the explicit V8.2 decisions below are now **approved only for the bounded ticket/report/appeal database redaction lifecycle**. No legal-compliance or universal erasure claim follows. V8.3 subject requests and V8.4–V8.6 remain separate. The inventory and roadmap are in [`V8-DESIGN.md`](V8-DESIGN.md); implemented columns live in `src/core/database/schema.ts`.

## Approved boundaries

- **OFF for every guild by default.** Migration 0018 never redacts existing records. New and existing guilds require actual GUILD_OWNER preview of proposed windows followed by explicit confirmation before enabling. Eiren ADMIN may view safe status/counts but may not enable, disable, change windows or set/remove holds. Discord Administrator and BOT_OWNER alone do not grant the actual guild owner's authority. Changing active windows requires a new preview and confirmation; disabling is immediate and version-fenced.
- **Approved windows use database time and terminal timestamps:** ticket transcript 90-day default (owner range 30–365) after `CLOSED/closed_at`; closed report narrative 365-day default (90–730) after `CLOSED/closed_at`; reviewed appeal narrative 365-day default (90–730) after `ACCEPTED` or `REJECTED/reviewed_at`. Open, reopened, under-review, pending or NULL-terminal records are ineligible. No zero-day/immediate redaction.
- The bounded single-process PostgreSQL worker is **tenant-scoped and transactionally fenced**: no deletion of parent records, only approved payload columns changed; lock policy row then target row, recheck current version/window/status/terminal DB time/hold/payload before mutation, and insert a unique metadata-only receipt in the same transaction. Maximum per scheduler pass is 100 each ticket/report/appeal redactions plus 500 each old receipts/previews. A rotating serviceable window of at most **5 enabled guilds**, capped at **20 candidates per guild/domain**, prevents an early tenant backlog from starving later tenants; more than 100 enabled guilds continue across successive passes. Selection/pruning use stable PostgreSQL statement time for indexed range bounds, with fresh DB time rechecked after target locking. Each maintenance query has local 1-second lock and 5-second statement timeouts so contention fails the isolated stage rather than blocking future ticks forever. No Discord I/O or recursive drain. A durable 15-minute owner preview stores safe counts; confirmation rechecks counts and policy version, consumes the preview, increments version and enables. Future eligibility under the active policy is expected.
- **Precisely scoped NULL redaction:** ticket `transcript`; report `description`, `evidence_url`, `resolution_note`; appeal `reason`, `review_note`. Nullable report description and appeal reason represent terminal redaction only; submission still requires non-empty text. Preserve all lifecycle/status, IDs, case links, report category and assignment, ticket close reason and transcript-generated timestamp. Persistent redaction timestamp/policy-version markers outlive receipts. Additive migration 0019 leaves 0000–0018 unchanged and requires all approved secondary fields to be NULL whenever a redaction marker is set, an explicit non-NULL policy version, and no misleading held-and-redacted state. It adds checks/indexes only; inconsistent existing rows fail migration rather than being silently rewritten. Each atomic receipt holds only guild/domain/record ID/policy version/confirming guild-owner ID/time; prune after **730 days** in bounded batches. If receipt insertion fails, roll back redaction. Do not log removed payload or SQL.
- **Actual GUILD_OWNER-only record holds** on tickets, reports and appeals block redaction entirely, have no expiry, and remain until explicitly removed. Store held state, setter ID and timestamp, without free-text reason. ADMIN and owner can inspect at most 50 current guild-scoped holds (domain, record ID, setter, timestamp), with no private narrative; only the owner can set/clear them. A newly placed hold cannot restore an already redacted payload; reject it. Active cases/appeals, open tickets/reports and unrelated unresolved Automation `UNCERTAIN` evidence remain untouched. Moderation cases, case reasons and staff notes are **outside V8.2**.
- **Database-only redaction, not delete-everywhere.** PostgreSQL redaction does not remove Discord messages/channels, downloaded transcripts, screenshots, exported files, replicas, old backups or operator-created copies. Backup ownership/expiry, restore-time deletion replay and Discord-copy actions are not V8.2 features; the bot does not own backup uploads or embed dump credentials. User/subject erasure belongs to **V8.3**; no `/forget` or `/delete-me` here. AI provider stays null, Message Content intent off, and no Redis/queue/extra worker is authorized.

## Working classification — not authorization outside the six V8.2 payload columns

| Class | Examples and engineering treatment |
| --- | --- |

| **ACCOUNTABILITY** | Moderation cases/reasons, staff-note authorship/provenance, dashboard audit, governance receipts and Automation execution/uncertainty evidence. Public visibility does not erase participant privacy or pending-result/replay obligations; DB and Discord copies require separate handling. `src/core/database/schema.ts`. |
| **LOW-CONTENT PERSONAL** | Analytics identifiers/aggregates, anti-raid join signals, XP/reputation/replay state, session metadata, AI metadata and other member-linked operational IDs. Low content is not anonymous; distinguish transient subject rows from aggregate/accountability records and preserve active anti-abuse bounds. `src/modules/analytics/repository.ts`, `src/modules/ai/retention.ts`, `src/core/database/schema.ts`. |

A subject request must inventory references by guild and distinguish the requester's eligible state from other people's reports, active abuse controls and accountability evidence. Neither a guild-admin action nor a subject request implies global one-click disappearance.

## Explicitly approved for V8.2

1. The **actual guild owner** alone controls preview confirmation, enabling/disabling, windows and record holds. ADMIN reads status/counts only. No role mapping or Discord Administrator permission delegates owner authority. An owner preview, exact confirmation checkbox/string and bounded recheck precede enabling or changing windows; disable is immediate and increments policy version.
2. Retention is **OFF** for old and new guilds. Windows are ticket 90 days (30–365), report and appeal 365 days (90–730), measured from authoritative terminal DB timestamps. No migration auto-enables or redacts a record.
3. Only the six listed ticket/report/appeal **database payload fields** are eligible; moderation cases/reasons and staff notes stay outside V8.2. A no-expiry owner hold blocks a record. Only metadata-only 730-day receipts are pruned automatically, up to 500 per pass. The owner remains the stored authorizer, not the scheduler.
4. Discord copies and backups are independently owned; no global erasure promise. Subject requests belong to V8.3. This does not approve an AI provider, new gateway intents or background infrastructure.

## V8.2 historical deferrals (V8.3 approval follows)

- Subject-request identity verification and per-user erasure, other domains (including moderation case reasons/notes), independent Discord-copy removal, and backup/replica deletion or replay require separately approved scope. V8.4 readiness/operations, V8.5 presentation redesign and V8.6 recovery drills remain separate.
- This is engineering policy, **not legal advice or a legal certification**. Production backups, TLS/proxy deployment, recovery time/point and replica controls are operator-owned and have not been proved by the synthetic CI rehearsal.

## Approved V8.3 — verified subject requests (not universal erasure)

- `/privacy request` and `/privacy status` are core, ephemeral guild commands, not an optional module. Creation derives the subject exclusively from `interaction.user.id`, force-fetches that same member from the current guild, and records `SELF_GUILD_MEMBER` verification with DB time. No staff/dashboard creation, arbitrary subject input, OAuth proof/token, modal or free-text reason. A verified request remains reviewable/executable if the subject subsequently leaves; governance never refetches that subject's membership.
- One active request per guild/subject (`PENDING`, `PREVIEWED`, `CONFIRMED`, `EXECUTING`), enforced by a partial unique index; concurrent self submissions safely resolve the same active row. Terminal `COMPLETED`, `PARTIAL`, `DENIED` permit a later new request; no new cooldown or permanent suppression list.
- ADMIN may read bounded metadata and create/refresh a preview. Only the **actual current guild owner** may confirm, execute or deny; BOT_OWNER, Discord Administrator and delegated rank do not bypass this. Dashboard uses fresh authorization, guild/request UUID scoping, POST, Origin, CSRF, rate/body bounds. Confirmation requires checkbox + `CONFIRM PRIVACY REQUEST`; execution requires another checkbox + `ERASE ELIGIBLE DATA`. Denial requires checkbox + `DENY PRIVACY REQUEST` and one fixed code: `NO_ELIGIBLE_DATA`, `ACCOUNTABILITY_REQUIRED`, `ACTIVE_OR_UNRESOLVED_STATE`, `OUT_OF_SCOPE`, `POLICY_RETAINED`.
- Workflow: self submission → `PENDING` → staff preview → `PREVIEWED` → owner confirmation → `CONFIRMED` → explicit owner execution → transactional `EXECUTING` → `COMPLETED`/`PARTIAL`; owner may deny before execution. Refreshing a confirmed preview removes the confirmation and requires fresh owner approval. Technical failure is never a denial. No automatic approval or background erasure.
- Durable previews last **15 minutes using PostgreSQL time**. Store fixed category/disposition counts and a SHA-256 digest of canonically sorted **structured record identities/role matches and safe state metadata only**, plus immutable request/guild/subject/preview-version binding. No transcript, narrative, reason, evidence URL, config/message content, fingerprint, credential/session-token hash or arbitrary JSON enters selection or digest. Both confirmation and execution recheck exact counts/hash/version, expiry and replay; changed inventory requires new preview/confirmation, never silently adds newly appeared rows to erasure.
- The five ERASE categories are `MEMBER_LEVEL_STATE`, `MEMBER_REPUTATION_AGGREGATE`, `ACHIEVEMENT_AWARDS`, `TERMINAL_EVENT_PARTICIPATION`, `TERMINAL_EVENT_ATTENDANCE`. Delete only that guild/subject's `member_levels`, `member_reputation`, `member_achievements`, and its own child rows of terminal-safe events. Profiles have no independent table. Levels deletion includes its XP/message/replay fields; assigned Discord reward roles remain. Reputation grants/cooldowns/replay history remain, old score is not reconstructed, and future grants may start a new aggregate. Read-only achievement views no longer award from historical evidence; future legitimate evaluation hooks may award again, including qualification based on retained history.
- Terminal-safe event means `COMPLETED`/`CANCELLED`, `presentation_pending = false`, `presentation_retry_at IS NULL`. Both participant and attendee ownership use `user_id`; another attendee's `marked_by = subject` is retained accountability. Lock relevant parents in deterministic ID order and recheck the predicates. Only participant count changes mark the existing parent presentation pending with NULL retry time; no event content/creator/status/other attendee changes, and **no Discord I/O in erasure**. Unresolved/active/scheduled children remain honestly retained, including when the events module is disabled. Existing reconciliation owns later aggregate presentation, not external-copy erasure.
- All primary erasure, receipt and final outcome commit in one SERIALIZABLE transaction, using parent-first event locks and the existing level advisory key/eligible row locks. Failure rolls back deletions, presentation invalidation and state; request remains safely CONFIRMED. Exactly one execution receipt per request; retries return safe terminal status without erasing again. This is a reviewed point-in-time snapshot, not a prohibition on later data creation.
- RETAIN categories are `MODERATION_ACCOUNTABILITY`, `REPORT_APPEAL_EVIDENCE`, `TICKET_ACCOUNTABILITY`, `VERIFICATION_ACCESS_STATE`, `ANTI_ABUSE_OR_REPLAY`, `REPUTATION_GRANT_HISTORY`, `SUGGESTION_HISTORY`, `STARBOARD_HISTORY`, `EVENT_CREATOR_ACCOUNTABILITY`, `EVENT_STAFF_ACCOUNTABILITY`, `ACTIVE_EVENT_STATE`, `UNRESOLVED_EVENT_PRESENTATION`, `GIVEAWAY_HISTORY`, `TEMPVOICE_OPERATIONAL_STATE`, `ANALYTICS_OPERATIONAL_STATE`, `GOVERNANCE_AUDIT`, `RETENTION_GOVERNANCE`, `AI_ACCOUNTING`, `AUTOMATION_ACCOUNTABILITY`, `AUTOMATION_UNCERTAIN`, `CONFIGURATION_ACCOUNTABILITY`, `OUT_OF_SCOPE`, `PRIVACY_GOVERNANCE`. These are static machine-readable codes, not free-text reasons. Moderation cases/reasons/notes, reports/evidence/appeals, tickets and participants, suggestion votes/content, reputation grants, giveaway/draw/winner history, starboard, verification/anti-abuse, analytics operational state, authorizers/configuration, AI accounting, Automation/UNCERTAIN and dashboard/V8.2 governance are **not erased or anonymized**. The complete structured-field boundary is recorded in `SUBJECT-REFERENCE-INVENTORY.md`; arbitrary text/JSON is never scanned. Guild-associated dashboard sessions are retained OUT_OF_SCOPE without selecting token hashes; global sessions unassociated with this guild remain outside this guild inventory and are never deleted.
- **Explicitly approved bookkeeping clarification:** the CURRENT request's mandatory identity/verification/preview/receipt evidence and exactly correlated privacy audit/gap rows remain retained and displayed separately, excluded only from that request's primary inventory digest/outcome. Correlation requires its exact UUID and fixed action/target-type contract, never a timestamp/action-prefix heuristic. Historical/other governance is still inventoried. Thus COMPLETED means no retained primary inventory references remain; PARTIAL means approved erasure completed but retained primary references remain, even with zero eligible rows. Neither outcome claims that mandatory workflow evidence disappeared.
- Receipts store only request/guild/subject IDs, authorizers, digest/version, execution time/outcome, five deleted counts and retained total. Terminal requests, execution receipts and governance gaps retain metadata **730 days**; nonterminal requests never age-prune. Cleanup only: <=500 expired/consumed previews after 24h, <=500 terminal request + receipt records combined (at most 250 parents and their receipts, only after preview cleanup), <=500 old audit gaps per pass, using DB time and bounded timeouts. No new process, per-request timer or asynchronous erasure worker.
- If a privacy governance mutation (or reused V8.2 confirm/disable/hold mutation) commits but DashboardAudit fails, persist a metadata-only audit gap; **never retry the domain mutation**. If gap persistence also fails, emit only request ID, action and error type. No form/body/narrative or existing audit deletion. V8.4 operational surfacing remains separate.
- The request concerns **Eiren-controlled primary PostgreSQL data for one guild**, not legal certification, permanent global erasure or account deletion. Discord messages/copies/roles, screenshots, downloads/exports and historical backups may remain. Future activity may recreate XP, reputation, achievements and event participation. No subject export, backup deletion/replay, AI provider, localization, new intent, Redis, worker, readiness or visual redesign. V8.4–V8.6 remain deferred. Migration 0020 is additive schema/index only: no subject request creation, erasure, policy enablement or V8.2 hold/receipt mutation.
