# V7 foundation validation ledger (V7.1 and V7.2A)

## Scope and baseline

V7.1 is implemented on `feature/v7-ai-automation` from merged V6 SHA `146a6ac4c183726d3597abb09ac55bf5a6490cb8`. It introduces **no usable AI replies or automation executions**. `ai` and `automation` are independent, disabled-by-default module definitions with no V7 commands, Discord events, components, dashboard pages, provider gateway, scheduler job, member-join trigger, external AI request, Redis, vector storage or script/HTTP action. The existing internal Eiren permission hierarchy remains authoritative; Discord Administrator does not grant Eiren ADMIN. No Message Content or additional privileged intent is introduced.

## Contracts and limits

The server-only optional `AI_ENABLED=false` default needs no provider credentials. Enabled infrastructure validates provider/model identifiers, a server-approved model catalog with operator-maintained price/cap metadata, HTTPS endpoint, private environment key, 15-second maximum timeout, and bounded process/guild concurrency. No provider SDK or HTTP adapter is wired. The live service receives only a sanitized admission configuration: neither endpoint nor API key is passed into its service-facing DTO. `AiRequest` keeps trusted instructions separate from untrusted user/context fields; output contains a finish reason, usage and optional safe provider request identifier. Future AI replies are to be ephemeral only; no `/ai ask`, `/ai summarize`, public publishing or moderation assistance exists in this phase.

Central hard limits: 4,000 input characters, 2,048 estimated input tokens, 512 output tokens, 25 guild requests per UTC day, 10 user requests per UTC day, 30-second user cooldown, one concurrent guild request, future process target four, operator-approved monthly per-guild budget no greater than US$5 and independent bounded operator global daily/monthly spending ceilings. A provider's price is **never assumed**; it must come from the validated server-only catalog. Guild rows may only lower server limits. The `AI_ENABLED` emergency flag takes effect on restart; no provider can be contacted by V7.1.

The Automation typed registries are intentionally empty/non-executable. Their contract distinguishes configure-time Eiren ADMIN authority, approved runtime capability and runtime bot prerequisites. Strict config schemas, finite static limits and bounded status transitions reject unsafe/unknown definitions; there is no executor. Future ceilings are 20 enabled rules/guild, two actions/rule, two causation levels, 1,000-character static messages, at most 20 due claims/tick and two/guild/tick, 10 executions/minute and 60/hour/guild, five retries. V7.1 stores capability, authorizer and config version for later reauthorization; historical ADMIN status by itself confers no future runtime authority. No role-grant action is registered.

## PostgreSQL and privacy model

Additive migration `drizzle/0014_perpetual_luckman.sql` and the corresponding journal/snapshot define seven new tables. Applied migrations `0000`–`0013` are untouched:

- `ai_settings`: guild-scoped approved provider/model names and optional lower limits, **not credentials**.
- `ai_usage_daily`: UTC date plus nonnegative accepted/rejected counts, reserved/settled micro-USD and token totals.
- `ai_requests`: bounded user/request-key/epoch/lease/status/cost/token **metadata only**; unique guild/request key, guild/date FK and cooldown/retention indexes. No prompt, response or raw message content.
- `automations`, `automation_actions`, `automation_executions`, `automation_action_runs`: guild-scoped configuration/capability/version, two-action positions, unique trigger replay key, bounded statuses/depth/attempts, composite guild+automation FK, typed/size-bounded JSON and expiry/due indexes. No executable code, AI text, arbitrary HTTP requests or message bodies.

`AiRepository.reserveIngress()` reads `guild_modules.enabled/version` under the module row lock in a short transaction. `AiRepository.admit()` obtains a short global spend advisory lock, then the same guild module row lock, checks the original immutable ingress epoch and approved settings/model, enforces cooldown/user/guild/global quotas, reserves worst-case priced spend and writes metadata in one transaction. A concurrent admission cannot both spend the final slot. A read-only review caught a separate cross-guild concurrency gap: the first implementation enforced one concurrent request per guild but not its configured process/global ceiling. A deterministic real-PostgreSQL two-guild race failed on `globalConcurrentAdmissionsRespectProcessTarget` before correction; under the existing global transaction lock, the repository now counts all live reservations before accepting another. The regression then passed. No DB lock survives a future provider operation. `settle()` releases exactly one reservation and records actual metadata or conservatively charges full cost for missing usage/expired leases; a disable/re-enable during work suppresses output authorization while still accounting incurred spend. Rejected/old-epoch attempts never record request metadata. No retention scheduler for these new tables runs in V7.1; indexes and explicit terminal statuses support a future bounded prune before any user-facing AI launches.

## Observed V7.1 validation

Complete final run passed `pnpm typecheck`, `pnpm test` (**312/312 tests in 43 files**), `pnpm build`, `pnpm db:check`, `pnpm db:migrate` (also safe on rerun), `pnpm db:smoke`, `pnpm db:v6` (**69/69 prior-version PostgreSQL assertions**), `pnpm db:v7` (**58/58 new real PostgreSQL assertions after the bounded V7.1 review**) and `pnpm dashboard:check` (all loopback checks true). `db:v7` uses synthetic guilds and deletes them in `finally`, including on assertion failure; it verifies guild/FK scoping, no content/secret columns, atomic quota and cross-guild spend/concurrency races, disabled/stale epochs, settlement and nonnegative accounting, automation shape/capability/status constraints, dedupe and cascade cleanup. A first local `0014` migration attempt failed with PostgreSQL code `42830`: the generated composite automation FK preceded creation of its target unique index. Reordering that index **within the new unapplied-to-operators V7 migration** resolved the issue; `pnpm db:check` and actual migration subsequently passed. Previously applied migrations `0000`–`0013` were not modified.

A bounded run of the **original V7.1 rebuilt bot** reported dashboard listening on `127.0.0.1:3000`, Discord gateway ready, voice analytics startup reconciliation, an initial analytics scheduler pass and two later approximately 30-second analytics ticks without errors. The process invoked its installed SIGINT shutdown handler, logged `Shutdown complete`, exited 0, and left zero listeners on port 3000. This bounded review changes only AI admission timing, model-price validation, PostgreSQL checks and this ledger; startup/wiring is unchanged. No AI provider gateway or automation executor was registered, so no provider request or automation action was possible in this V7.1 runtime. This is not evidence of real AI behavior, enabled-guild analytics, authenticated dashboard mutations or live human voice.

## Bounded V7.1 safety review

The review reproduced a concrete lease/cost boundary failure with a real PostgreSQL advisory-lock hold: admission created a lease from a timestamp captured **before** waiting for the lock, and settlement could authorize an already-expired reservation. Default production time is now sampled after acquiring the global lock and guild module row for admission, and after locking the request row for settlement. The service DTO does not accept or forward a caller-supplied clock; explicit repository-only test timestamps still support deterministic UTC-boundary checks. The review also reproduced acceptance of a zero-priced operator model, which could bypass spending ceilings if misconfigured for a future provider; both catalog validation and `maximumCostMicros()` now reject zero, negative, nonfinite and oversized prices. Focused regressions reproduced failures before each correction, then passed afterward.

`db:v7` additionally tests a held-lock admission lease, held-lock expiry at settlement, concurrent duplicate settlements, settlement racing with expiry cleanup, exact nonnegative counters, distinct-key same-guild concurrency when daily quota has room, simultaneous request-key replay and cooldown across UTC midnight. It checks that expiration conservatively moves reserved cost to settled cost once, without authorizing output after the lease. These synthetic checks use no real provider or user content and remove their fixtures.

**V7.1-only note:** Before V7.2A, bounded retention of terminal `ai_requests` and daily usage was still required. V7.2A adds that pruning without provider traffic; see below. On process restart there is no continuing provider call; the persisted model ID, token bounds and immutable reserved cost permit safe pessimistic orphan expiry. A future adapter must not recompute an old in-flight request using a changed catalog price: retain ingress-time pricing/identity during live work and charge the full reservation when trusted original usage/pricing is unavailable. Future automation execution (V7.3) must recheck current authorization, bot capabilities, module epoch, configuration version and registry schemas before effects; bind action-run positions to actual configured actions and apply bounded claims/retention. None of these deferred execution paths was active in V7.1.

## V7.2A explicit request lifecycle (no production provider)

`/ai ask prompt:<text>` and `/ai summarize text:<text>` use only explicit slash-option strings; `/ai status` reports safe module/provider availability even when the module is disabled. The dispatcher captures immutable AI ingress **before optional analytics, deferReply, member lookup or module checks**, then passes the original token (never a refreshed epoch) to the command. Dispatcher permission is MEMBER+, the admission service rechecks actor/permission and PostgreSQL module epoch, and the AI request is declined without a provider call when stale. Production injects **no provider adapter** (`null`), so even an enabled module cannot send a real inference request; a network-free local fake is injected only by tests. No key, SDK, provider HTTP call, vector store, Message Content intent or Automation runtime is added. Test bootstrap writes synthetic server-approved provider/model IDs directly to a temporary guild's `ai_settings` row; there is no MEMBER-facing configuration mutation or dashboard UI.

The orchestrator estimates input tokens conservatively as UTF-8 byte length (at most 2,048, alongside the 4,000 UTF-16-code-unit ceiling). This may decline text that a tokenizer could accept; it never silently truncates. A 512-output-token cap and at most 15-second AbortController timeout apply. Ask/summarize trusted instructions are fixed short server strings; pasted text stays solely in `AiRequest.userInput`, not an instruction or implicit context. Fake output is accepted only with matching approved model ID, recognized finish reason, nonempty string <=1,800 display characters and positive integer input/output usage within the reservation. A token-limit finish reason adds an explicit bounded indicator rather than silently truncating. Invalid/missing usage, throw, timeout, abort, oversized response or ambiguous dispatch consumes the full reserved cost; a reliable valid result settles actual bounded usage. An already-disabled/reenabled epoch can still be billed for an attempted provider call, but `settle()` refuses output authorization. Replies are dispatcher-deferred ephemeral edits with `allowedMentions: { parse: [] }`, no public posting, attachment or transcript. Provider/driver error text and IDs are not displayed or logged. A missing provider returns a safe unavailable result without reserving a request.

**Metadata retention:** one global `ai-maintenance` scheduler job runs every 30-second tick regardless of module/provider setting or cached Discord guilds. In one global-advisory-lock transaction it terminalizes up to 500 abandoned `RESERVED` rows older than 30 days whose leases have expired, moving their full reserved cost into settled cost once; deletes at most 500 `SETTLED`/`EXPIRED` requests older than 30 days; then deletes at most 500 unreferenced `ai_usage_daily` rows older than 13 UTC calendar months. Active reservations and days with request FK references survive. One bounded pass per tick, no unlimited loop or per-guild timer. Scheduler failure logs only a safe job/stage/error type. Current `0014` created-at and UTC-day indexes support bounded pruning; **no 0015 migration is necessary** and migrations `0000`–`0014` are unchanged. Pruning is blocked by the same advisory lock as admission/settlement, so it cannot delete an unsettled request during a valid settlement. Request-key replay protection lasts while request metadata is retained; any future adapter must account for the Discord replay horizon and prune policy. AI metadata has no content; existing non-AI logs/audits keep their separately documented retention semantics.

V7.2A fake-provider tests exercise success, injection-as-data, delay, abort/timeout, throw, missing/invalid/over-reservation usage, output bounds, disabled/reenabled epoch, concurrent replay, and safe command replies. Real PostgreSQL checks exercise 30-day/13-month retention, bounded batches, live-row/FK preservation, prune-versus-settle, and fake ask/summarize/epoch transitions using synthetic approved guild settings. **These do not demonstrate external provider interoperability or AI answer quality**; choosing/integrating a remote provider and real credentials remains V7.2B. A bounded run of the final rebuilt bot logged gateway readiness, dashboard listening on loopback port 3000, voice analytics startup reconciliation, an initial analytics pass plus two later ~30-second scheduler ticks, and `ai-maintenance` on all three passes (`expired=0`, `requestsPruned=0`, `usageDaysPruned=0`) without errors. The installed SIGINT shutdown handler logged `Shutdown complete`, exited 0, and port 3000 had zero listeners afterward. No external AI request could occur: production instantiated `AiRuntime(ai, null)`. `/ai status` was covered by deterministic dispatcher tests, not exercised as a live human Discord interaction.
