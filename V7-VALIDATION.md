# V7 foundation validation ledger (V7.1 and V7.2A)

## Scope and baseline

V7.1 is implemented on `feature/v7-ai-automation` from merged V6 SHA `146a6ac4c183726d3597abb09ac55bf5a6490cb8`. It introduces **no usable AI replies or automation executions**. `ai` and `automation` are independent, disabled-by-default module definitions with no V7 commands, Discord events, components, dashboard pages, provider gateway, scheduler job, member-join trigger, external AI request, Redis, vector storage or script/HTTP action. The existing internal Eiren permission hierarchy remains authoritative; Discord Administrator does not grant Eiren ADMIN. No Message Content or additional privileged intent is introduced.

## Contracts and limits

The server-only optional `AI_ENABLED=false` default needs no provider credentials. Enabled infrastructure validates provider/model identifiers, a server-approved model catalog with operator-maintained price/cap metadata, HTTPS endpoint, private environment key, 15-second maximum timeout, and bounded process/guild concurrency. No provider SDK or HTTP adapter is wired. The live service receives only a sanitized admission configuration: neither endpoint nor API key is passed into its service-facing DTO. `AiRequest` keeps trusted instructions separate from untrusted user/context fields; output contains a finish reason, usage and optional safe provider request identifier. Future AI replies are to be ephemeral only; no `/ai ask`, `/ai summarize`, public publishing or moderation assistance exists in this phase.

Central hard limits: 4,000 input characters, 2,048 estimated input tokens, 512 output tokens, 25 guild requests per UTC day, 10 user requests per UTC day, 30-second user cooldown, one concurrent guild request, future process target four, operator-approved monthly per-guild budget no greater than US$5 and independent bounded operator global daily/monthly spending ceilings. A provider's price is **never assumed**; it must come from the validated server-only catalog. Guild rows may only lower server limits. The `AI_ENABLED` emergency flag takes effect on restart; no provider can be contacted by V7.1.

The Automation typed registries are intentionally empty/non-executable. Their contract distinguishes configure-time Eiren ADMIN authority, approved runtime capability and runtime bot prerequisites. Strict config schemas, finite static limits and bounded status transitions reject unsafe/unknown definitions; there is no executor. Future ceilings are 20 enabled rules/guild, two actions/rule, two causation levels, 1,000-character static messages, at most 20 due claims/tick and two/guild/tick, 10 executions/minute and 60/hour/guild, five retries. V7.1 stores capability, authorizer and config version for later reauthorization; historical ADMIN status by itself confers no future runtime authority. No role-grant action is registered.

## PostgreSQL and privacy model

Additive migration `drizzle/0014_perpetual_luckman.sql` and the corresponding journal/snapshot define seven new tables. Applied migrations `0000`–`0013` are untouched:

- `ai_settings`: guild-scoped approved provider/model names and optional lower limits, **not credentials**.
- `ai_usage_daily`: UTC date plus nonnegative accepted/rejected counts, reserved/settled micro-USD and token totals.
- `ai_requests`: bounded user/request-key/epoch/lease/status/cost/token **metadata only**; unique guild/request key, guild/date FK and cooldown/retention indexes. No prompt, response or raw message content.
- `automations`, `automation_actions`, `automation_executions`, `automation_action_runs`: guild-scoped configuration/capability/version, two-action positions, unique trigger replay key, bounded statuses/depth/attempts, composite guild+automation FK, typed/size-bounded JSON and expiry/due indexes. No executable code, AI text, arbitrary HTTP requests or message bodies.

`AiRepository.reserveIngress()` reads `guild_modules.enabled/version` under the module row lock in a short transaction. `AiRepository.admit()` obtains a short global spend advisory lock, then the same guild module row lock, checks the original immutable ingress epoch and approved settings/model, enforces cooldown/user/guild/global quotas, reserves worst-case priced spend and writes metadata in one transaction. A concurrent admission cannot both spend the final slot. A read-only review caught a separate cross-guild concurrency gap: the first implementation enforced one concurrent request per guild but not its configured process/global ceiling. A deterministic real-PostgreSQL two-guild race failed on `globalConcurrentAdmissionsRespectProcessTarget` before correction; under the existing global transaction lock, the repository now counts all live reservations before accepting another. The regression then passed. No DB lock survives a future provider operation. `settle()` releases exactly one reservation and records actual metadata or conservatively charges full cost for missing usage/expired leases; a disable/re-enable during work suppresses output authorization while still accounting incurred spend. Rejected/old-epoch attempts never record request metadata. No retention scheduler for these new tables runs in V7.1; indexes and explicit terminal statuses support a future bounded prune before any user-facing AI launches.

## Bounded V7.1 safety review

The review reproduced a concrete lease/cost boundary failure with a real PostgreSQL advisory-lock hold: admission created a lease from a timestamp captured **before** waiting for the lock, and settlement could authorize an already-expired reservation. Default production time is now sampled after acquiring the global lock and guild module row for admission, and after locking the request row for settlement. The service DTO does not accept or forward a caller-supplied clock; explicit repository-only test timestamps still support deterministic UTC-boundary checks. The review also reproduced acceptance of a zero-priced operator model, which could bypass spending ceilings if misconfigured for a future provider; both catalog validation and `maximumCostMicros()` now reject zero, negative, nonfinite and oversized prices. Focused regressions reproduced failures before each correction, then passed afterward.

`db:v7` additionally tests a held-lock admission lease, held-lock expiry at settlement, concurrent duplicate settlements, settlement racing with expiry cleanup, exact nonnegative counters, distinct-key same-guild concurrency when daily quota has room, simultaneous request-key replay and cooldown across UTC midnight. It checks that expiration conservatively moves reserved cost to settled cost once, without authorizing output after the lease. These synthetic checks use no real provider or user content and remove their fixtures.

**V7.1-only note:** Before V7.2A, bounded retention of terminal `ai_requests` and daily usage was still required. V7.2A adds that pruning without provider traffic; see below. On process restart there is no continuing provider call; the persisted model ID, token bounds and immutable reserved cost permit safe pessimistic orphan expiry. A future adapter must not recompute an old in-flight request using a changed catalog price: retain ingress-time pricing/identity during live work and charge the full reservation when trusted original usage/pricing is unavailable. Future automation execution (V7.3) must recheck current authorization, bot capabilities, module epoch, configuration version and registry schemas before effects; bind action-run positions to actual configured actions and apply bounded claims/retention. None of these deferred execution paths was active in V7.1.

## V7.2A explicit request lifecycle (no production provider)

`/ai ask prompt:<text>` and `/ai summarize text:<text>` use only explicit slash-option strings; `/ai status` reports safe module/provider availability even when the module is disabled. The dispatcher captures immutable AI ingress **before optional analytics, deferReply, member lookup or module checks**, then passes the original token (never a refreshed epoch) to the command. Dispatcher permission is MEMBER+, the admission service rechecks actor/permission and PostgreSQL module epoch, and the AI request is declined without a provider call when stale. Production injects **no provider adapter** (`null`), so even an enabled module cannot send a real inference request; a network-free local fake is injected only by tests. No key, SDK, provider HTTP call, vector store, Message Content intent or Automation runtime is added. Test bootstrap writes synthetic server-approved provider/model IDs directly to a temporary guild's `ai_settings` row; there is no MEMBER-facing configuration mutation or dashboard UI.

**Historical V7.2A behavior at `e2757cb`:** the orchestrator estimated only the user text as UTF-8 bytes, capped at 2,048 (and 4,000 UTF-16 code units). This omitted instructions and framing from the pre-dispatch cost reservation. The corrective section below supersedes this estimate; no text is silently truncated. A 512-output-token cap and at most 15-second AbortController timeout apply. Ask/summarize trusted instructions are fixed short server strings; pasted text stays solely in `AiRequest.userInput`, not an instruction or implicit context. Fake output is accepted only with matching approved model ID, recognized finish reason, nonempty string <=1,800 display characters and positive integer input/output usage within the reservation. A token-limit finish reason adds an explicit bounded indicator rather than silently truncating. Invalid/missing usage, throw, timeout, abort, oversized response or ambiguous dispatch consumes the full reserved cost; a reliable valid result settles actual bounded usage. An already-disabled/reenabled epoch can still be billed for an attempted provider call, but `settle()` refuses output authorization. Replies are dispatcher-deferred ephemeral edits with `allowedMentions: { parse: [] }`, no public posting, attachment or transcript. Provider/driver error text and IDs are not displayed or logged. A missing provider returns a safe unavailable result without reserving a request.

**Metadata retention:** one global `ai-maintenance` scheduler job runs every 30-second tick regardless of module/provider setting or cached Discord guilds. In one global-advisory-lock transaction it terminalizes up to 500 abandoned `RESERVED` rows older than 30 days whose leases have expired, moving their full reserved cost into settled cost once; deletes at most 500 `SETTLED`/`EXPIRED` requests older than 30 days; then deletes at most 500 unreferenced `ai_usage_daily` rows older than 13 UTC calendar months. Active reservations and days with request FK references survive. The scheduler **does not immediately terminalize a newly expired lease**: its `RESERVED` scan also requires request age greater than 30 days. Normal admissions perform expired-reservation recovery independently under the same lock. One bounded pass per tick, no unlimited loop or per-guild timer. Scheduler failure logs only a safe job/stage/error type. Current `0014` created-at and UTC-day indexes support bounded pruning; **no 0015 migration is necessary** and migrations `0000`–`0014` are unchanged. Pruning is blocked by the same advisory lock as admission/settlement, so it cannot delete an unsettled request during a valid settlement. Request-key replay protection lasts while request metadata is retained; any future adapter must account for the Discord replay horizon and prune policy. AI metadata has no content; existing non-AI logs/audits keep their separately documented retention semantics.

V7.2A fake-provider tests exercise success, injection-as-data, delay, abort/timeout, throw, missing/invalid/over-reservation usage, output bounds, disabled/reenabled epoch, concurrent replay, and safe command replies. Real PostgreSQL checks exercise 30-day/13-month retention, bounded batches, live-row/FK preservation, prune-versus-settle, and fake ask/summarize/epoch transitions using synthetic approved guild settings. **These do not demonstrate external provider interoperability or AI answer quality**; choosing/integrating a remote provider and real credentials remains V7.2B. Final complete V7.2A validation passed: `pnpm typecheck`, `pnpm test` (**348/348 tests across 46 files**), `pnpm build`, `pnpm db:check`, `pnpm db:migrate`, `pnpm db:smoke`, `pnpm db:v6` (**69/69 assertions**), `pnpm db:v7` (**58 existing + 9 retention + 7 fake-runtime = 74/74 real PostgreSQL assertions**), and `pnpm dashboard:check` (all loopback checks true). A bounded run of the final rebuilt bot logged gateway readiness, dashboard listening on loopback port 3000, voice analytics startup reconciliation, an initial analytics pass plus two later ~30-second scheduler ticks, and `ai-maintenance` on all three passes (`expired=0`, `requestsPruned=0`, `usageDaysPruned=0`) without errors. The installed SIGINT shutdown handler logged `Shutdown complete`, exited 0, and port 3000 had zero listeners afterward. No external AI request could occur: production instantiated `AiRuntime(ai, null)`. `/ai status` was covered by deterministic dispatcher tests, not exercised as a live human Discord interaction.

## V7.2A pre-provider accounting correction (after `e2757cb`)

**Reproduced gap:** the original runtime reserved only `Buffer.byteLength(userInput, 'utf8')`. Its trusted ask/summarize instructions and future explicit context were omitted, as was chat/request framing. An operator cap or budget headroom sufficient for user-only text could therefore admit a request whose complete input costs more than its reservation. Settlement rejecting over-reported usage is **too late**: the provider dispatch has already incurred possible spend and the quota was never held. Production still injects `null`, so this was a pre-provider blocker, not observed external spend.

**Corrected invariant:** `prepareAiRequest()` constructs one frozen canonical description (selected model, fixed trusted instructions, explicit untrusted user input, optional explicit untrusted context, max output, and complete estimated billable input) **before admission**. UTF-8 byte lengths of all three text fields are added to an operator-approved `requestOverheadTokens` per model (an integer from 0 through 512). Server catalog parsing requires it explicitly; guilds cannot change it. A provider capability can require at most the approved allowance or the runtime refuses the adapter. The admission service independently re-estimates the same fields, rejects mismatched/forged estimates, and sends only bounded counts—not content—to PostgreSQL. Provider dispatch copies these very same prepared fields; it cannot reconstruct a larger unreserved prompt in this runtime. The repository persists `reserved_input_tokens` equal to this total and reserves `maximumCostMicros(approvedModel, totalInput, maxOutput)` with pre-existing positive-price validation, BigInt arithmetic and upward micro-unit rounding. The immutable admission exposes that reserved input bound, which provider usage must not exceed; valid actual usage can legitimately exceed the **user-only** byte count while staying within the complete bound. Missing/invalid/excess usage consumes the full reservation.

The 2,048 `maxEstimatedInputTokens` ceiling means **total complete request input**, not maximum user text. Both that policy ceiling and `model.maxInputTokens` apply before admission/provider dispatch; model output cap applies separately. Conservative over-rejection is intentional. This byte-plus-approved-envelope approach is not a proof of equivalence to a future provider tokenizer. **V7.2B must prove, locally and without a provider response, that its concrete serialized request tokenization and framing cannot exceed its declared operator-approved allowance and the complete reservation before it can be wired**; the generic contract alone cannot establish an external vendor's billing semantics. No network estimator, remote SDK or real provider was added.

Focused tests reproduce the original `5`-token user-only admission for `Hello` and verify the complete estimate is larger after the fix. Preparation/fake tests cover variable trusted instructions, user input, explicit context separated from instructions, nonnegative bounded framing, malformed allowances, 2,048 total ceiling, smaller model input limit, full-input-plus-max-output pricing, valid fake usage greater than user-only but within reservation, and conservatively failed usage above the total. Real PostgreSQL checks add an old-user-only-fits/new-complete-rejects model-cap fixture and a daily-budget fixture where user-only reservation fits but instruction-plus-framing reservation exceeds the guild budget: no request or reserved spend and no fake provider call. An independent isolated old-estimate control **does** admit the user-only reservation under the same guild cap, proving the regression would have failed before the correction. The synthetic accepted request's persisted reserved token count and cost are verified against its complete prepared input. No migration was required; `reserved_input_tokens` already exists in `0014` and migrations `0000`–`0014` remain unchanged.

Final correction validation passed **361/361 tests in 47 files** (baseline 348), `pnpm typecheck`, `pnpm build`, `pnpm db:check`, `pnpm db:migrate`, `pnpm db:smoke`, `pnpm db:v6` (**69/69 PostgreSQL assertions**) and `pnpm db:v7` (**58 foundation + 9 retention + 13 fake-runtime = 80/80 PostgreSQL assertions**, baseline 74), plus `pnpm dashboard:check` with all loopback checks true. The rebuilt bot still initializes `new AiRuntime(ai, null)` with no external AI request path: a bounded existing-config startup logged dashboard listener and Discord gateway readiness, handled SIGINT cleanly with exit code 0, and left port 3000 free. No real provider call or credential was used.

## V7.3 Automation Core (NO Discord automation actions)

V7.3 registers **inert** typed SCHEDULED v1, STATIC_MESSAGE v1 and STAFF_LOG v1 definitions (`runnable: false`) with strict Zod JSON, ADMIN configure permission, required runtime capability/prerequisite metadata, bounded timeout and idempotency classifications. Their action names declare future intent; neither registry nor scheduler invokes a Discord send, staff log, role operation, webhook, HTTP action, AI provider, script or arbitrary code. The AI provider remains null and AI settings/quotas/behavior are unchanged. Automation and AI remain independent and default-disabled. There are deliberately **no management slash commands or V7 dashboard controls** yet; internal `AutomationService` is the guarded CRUD surface.

`AutomationService` requires Eiren ADMIN+ for create, inspect/list, full update, enable/disable, soft delete and explicit execution creation. Discord Administrator alone is not an Eiren ADMIN. Every repository lookup/mutation carries `guildId + automationId` and the existing composite execution FK prevents cross-guild rows. Rule creation/update validates names (1–80), <=2 actions, approved key/version/schema, max 1,000 configured static-message characters, matching valid IANA timezone, bounded 0–86,400-second cooldown, strict safe configuration JSON and capability **derived from registered actions** rather than caller text. Under a transaction-level lock, <=20 rules may be enabled per guild. Config-affecting mutations and individual enable/disable increment `config_version`. Soft deletion increments it again and retains rule/actions and execution/snapshot history; normal service reads hide deleted rules. Existing 0014 physical FK cascades still apply to a direct DBA/guild deletion, not a service soft delete.

SCHEDULED supports only a strict daily `HH:MM` in the configured IANA zone and a one-time ISO UTC `Z` timestamp—**not cron**. Pure next-occurrence computation skips nonexistent spring-forward wall time and selects only the earlier instance of a repeated fall-back wall time. Next run is stored in UTC; re-enable computes a strictly future occurrence. One bounded global scheduler job uses the existing ~30-second wakeup, creates at most one occurrence for each selected due rule (maximum 20 candidates per tick), advances straight to the next future occurrence and never drains an unlimited backlog. Its deterministic `scheduled:<UTC timestamp>` key plus `(guildId,automationId,triggerKey)` uniqueness prevents duplicate creation across workers. Enqueue and `next_run_at` advancement share one PostgreSQL transaction: failure rolls both back. When the module is disabled, due generation advances the schedule without enqueueing, so disabled time does not accrue a backlog. A completed one-time occurrence has `next_run_at = NULL`; re-enabling a past one-time schedule does not replay it. Execution rows capture original module epoch, rule config version, causation UUID, chain depth <=2, PENDING state and next attempt. Actions are snapshotted with position/key/version/bounded configured JSON in the same enqueue transaction; the snapshot cannot be updated, and the action-run `(executionId,position)` composite FK cannot name an unconfigured position. Final authorization revalidates the typed JSON, snapshot against current actions and unchanged config version.

Claiming is a short PostgreSQL transaction: ranked `FOR UPDATE OF e SKIP LOCKED` claims <=20 globally and <=2 per guild per tick, sets RUNNING/unique claim token/60-second lease and increments attempts. Production clocks are sampled **after advisory/guild-lock waits** when minting leases and **after finalization row-lock waits** when checking expiration, never from a timestamp captured before a delayed transaction. A global automation advisory transaction lock plus guild row serializes cross-worker rate reservations; indexed attempt metadata, bound by a composite `(guild_id, execution_id)` FK, enforces <=10 claims per guild per rolling minute and <=60 per rolling hour, including retries. Even a subsequently `SKIPPED` stale claim consumes a rate slot: reservation happens before the authority check and is intentionally conservative. No Discord/member REST call is held inside that transaction. **After commit**, a fresh forced Discord guild/member lookup obtains current membership and roles, then Eiren ADMIN is rechecked; missing/revoked membership cannot authorize. A second short transaction requires the original claim token/unexpired lease, current enabled module/unchanged `module_epoch`, enabled/undeleted rule/unchanged `config_version`, valid capability and snapshot. V7.3 records `SKIPPED CORE_ONLY` on an otherwise valid claim; stale or revoked claims are also skipped, **never executed**. Membership lookup failures defer without assuming authority.

Expired RUNNING leases are processed in bounded batches of 20. A claim with no started/finished/uncertain action-run can return to PENDING after deterministic 30, 60, 120, then 240-second backoff (with a 600-second general ceiling); at most five attempts and 24 hours of age. The legal RUNNING->PENDING transition is restricted to no-effect lease recovery or transient authority-lookup deferral after verifying no action run started; it is not a generic status update. A started/succeeded/uncertain action-run makes an expired execution UNCERTAIN, terminal with no blind retry. PENDING older than 24 hours fails before claim. Legal transitions are explicit; the exceptional FAILED->PENDING path is restricted by the repository to safe retryable internal failures before five attempts. Bounded pruning removes at most 200 rate-attempt rows older than an hour and 100 `SUCCEEDED`/`SKIPPED`/`FAILED` execution rows older than 90 days per tick; cascade deletes their attached snapshots/action runs. **Unresolved `UNCERTAIN` executions and their action-run/snapshot evidence are never pruned automatically**; future V7.4 must provide explicit manual reconciliation before any separate disposal policy. No arbitrary triggering content, AI text, ticket/report content or credentials is persisted in Automation metadata. Static configured action text is administrator-authored configuration, not captured private event content.

Additive migration **0015** creates immutable execution-action snapshots, rate-attempt metadata and a soft-delete column; the composite action-run FK binds positions to execution-owned snapshots. The V7.3 final review corrected its backfill: legitimate V7.1 inert runs may have lost their configured position, and present-day action JSON cannot prove their historic configuration. Every pre-0015 inert action run is now preserved with a **non-runnable `LEGACY_INERT`/`V7_1_UNVERIFIED` sentinel**, never misrepresented as a currently configured action; typed final authorization rejects that sentinel. Additive **0016** aligns the check on databases where 0015 already ran, invalidates any prior run-bound snapshot with unproven V7.1 provenance using the same sentinel, corrects misattributed attempt-guild metadata using the execution's authoritative guild, and adds the composite FK and supporting unique index. Migrations 0000–0014 are unchanged. This is a metadata and correctness foundation for V7.4, **not authorization to perform a real Discord action**. V7.4 must implement idempotent actual action dispatch, bot/channel permission checks, ambiguous message outcome reconciliation and any staff-facing management UI separately.
