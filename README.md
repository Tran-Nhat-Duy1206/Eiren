# Eiren — modular Discord bot (V6)

A TypeScript/discord.js modular monolith backed by PostgreSQL. V0 provides guild configuration, permissions and module gating; V1 adds moderation and logging; V2 adds verification and anti-raid protection; V3 adds optional role menus, tickets, reports/appeals and suggestions; V4 adds optional levels, reputation, starboard and read-only profiles; V5 adds events, giveaways, temporary voice rooms and cosmetic achievements; V6 adds optional guild analytics and an opt-in web dashboard. See [V0-VALIDATION.md](V0-VALIDATION.md), [V1-VALIDATION.md](V1-VALIDATION.md), [V2-VALIDATION.md](V2-VALIDATION.md), [V3-VALIDATION.md](V3-VALIDATION.md), [V4-VALIDATION.md](V4-VALIDATION.md), [V5-VALIDATION.md](V5-VALIDATION.md), and [V6-VALIDATION.md](V6-VALIDATION.md) for evidence and unverified checks.

## Requirements

Node.js 24+, pnpm 10+, Docker with Compose, and a Discord application/bot. Invite it with `bot` and `applications.commands` scopes. To activate `logging`, `verification`, or `antiraid`, **enable the privileged Server Members Intent** (`GuildMembers`) in the Discord Developer Portal, set `ENABLE_GUILD_MEMBERS_INTENT=true` in `.env`, and restart the bot. Without both, V0 and moderation still start; modules needing member events cannot be enabled rather than silently missing joins. The bot also requests Guilds, GuildMessages, GuildMessageReactions, GuildVoiceStates, and GuildModeration intents. Message Content intent is **not** requested; edits/deletes log IDs, not message text. V4 XP and starboard degrade safely without message content (see below). Grant the bot View Channel, Send Messages, Embed Links in configured log/verification channels; Manage Roles and a highest bot role above both verification roles; and Moderate Members, Kick Members, Ban Members, Manage Messages, Read Message History as required for moderation. Place its highest role above intended targets; Discord role hierarchy still applies. V5 events/giveaways also need View Channel, Send Messages, Embed Links and Read Message History in their configured public announcement channels; tempvoice needs View Channel, Manage Channels, Move Members and Connect for its configured lobby/category. Voice state events use the already requested GuildVoiceStates intent. Member lookups for command/giveaway eligibility use on-demand guild member fetch; no additional privileged member-event intent is requested by V5 itself. Without a privileged intent already enabled in the portal, the Discord gateway may reject login.

## Local start (from project root)

1. `pnpm install`
2. Copy `.env.example` to `.env`. Set your Discord token, application ID, private development guild ID, and a local database password. Use that same password in `POSTGRES_DEV_PASSWORD` (Docker Compose) and `DATABASE_URL` (URL-encode reserved characters). Do not commit `.env`.
3. `docker compose up -d postgres`
4. `pnpm db:migrate`
5. `pnpm db:smoke` verifies earlier-version tables, key constraints and rollback without retaining test data; run `pnpm db:v6` for the separate V6 database checks.
6. `pnpm commands:register` (guild-scoped registration takes effect quickly when `DISCORD_DEV_GUILD_ID` is set).
7. `pnpm dev` (or `pnpm build && pnpm start`). Stop with Ctrl+C for graceful cleanup.

Production command registration: omit `DISCORD_DEV_GUILD_ID`, run `pnpm commands:register`, then start the bot. Global command propagation can take time. **Do not switch a development guild to global registration without clearing its old guild-scoped commands**, or duplicate-looking commands may remain. Run migrations explicitly before deploying new code; the bot checks that its tables exist rather than applying migrations on startup. Keep the database URL and bot token secret.

## Commands and permissions

- `/setup`: guild owner only; transactional, idempotent creation of guild and settings; repeated calls preserve changes.
- `/config view`, `/config set`: mapped ADMIN or higher. `language` is `en` in V0; `timezone` accepts IANA names. For channel/role settings, pass a Discord ID or `clear`.
- `/config role-set`, `/config role-remove`, `/config roles`: guild owner only. Assign HELPER, MODERATOR, SENIOR_MODERATOR, or ADMIN to roles. GUILD_OWNER cannot be delegated.
- `/module enable`, `/module disable`, `/module list`: mapped ADMIN or higher; require setup. Core is permanently enabled. `moderation`, `logging`, `verification`, `antiraid`, `roles`, `tickets`, `reports`, `suggestions`, `levels`, `reputation`, `starboard`, `profiles`, `events`, `giveaways`, `tempvoice`, and `achievements` are optional modules, disabled by default. Only `antiraid` depends on `verification`; V3–V5 modules have no hard inter-module dependencies. Enable `verification` before `antiraid` (the manifest enforces the dependency). Enable `logging` and set `security_log_channel` to receive security alerts. Disabled commands, events and persistent button/select interactions are blocked at dispatch.

The guild owner retains owner authority regardless of mappings. Discord Administrator alone is **not** an implicit bot ADMIN. Permission mapping changes are restricted to the actual guild owner. Responses are ephemeral. A disabled module is blocked by command/event dispatchers; its registered slash command can still appear in Discord.

## V1 moderation

Enable `moderation` after `/setup`. The guild owner maps staff roles with `/config role-set`; bot permissions are *not* inferred from Discord Administrator. `/mod warn`, `/mod timeout`, `/mod kick`, `/mod purge`, `/mod note`, `/mod history`, and `/mod case` require MODERATOR. `/mod ban`, `/mod tempban`, and `/mod unban` require SENIOR_MODERATOR. The actor's Discord role must outrank a member target (unless the actor owns the guild), and the bot needs its own action permission and a higher role. Neither owner nor self can be moderated. `/mod purge` accepts 1–100 recent messages in the current text channel; Discord excludes messages older than 14 days. `/mod timeout` and `/mod tempban` accept durations such as `30m`, `2h`, or `1d`; timeout is capped at 28 days and tempban at one year. Every action creates a case; use `/mod history @user` or `/mod case id` to inspect it. `/mod note @user text` creates a private note, while omitting text lists notes to authorized staff only.

Temporary punishment cases and expiry claims are stored in PostgreSQL. A scheduler scans due cases after startup and every 30 seconds, with stale-claim recovery. Discord expires timeouts automatically; the bot avoids cancelling a subsequent manual extension. Tempban refuses to replace an already-existing ban and expiry unbans only a ban whose audit reason still contains that case ID, avoiding an unrelated later ban. Discord has no atomic conditional-ban API, so an external ban created between the final preflight and Discord's ban request remains a narrow concurrency limitation. Expiration continues even if the moderation module is disabled after a case was created. Run `pnpm db:migrate` before deploying new V1 code: migration `drizzle/0001_aberrant_wild_child.sql` is additive; never edit the applied V0 migration.

## V1 guild logging

After enabling the portal intent and setting `ENABLE_GUILD_MEMBERS_INTENT=true`, enable `logging` and set destination IDs via `/config set log_channel`, `/config set mod_log_channel`, and `/config set security_log_channel`. General logs include joins/leaves, message edits/deletes (IDs only), channel changes, and voice join/leave/move. Member nickname/role updates and bot moderation actions route to the moderation channel. The security channel is reserved for security-category entries; no security-alert producer exists in V1. Categories never fall back to another channel. Missing or inaccessible channels are skipped with internal warnings. No message content, credentials, or private staff notes are included in guild logs.

## V2 verification

With Server Members Intent enabled, configure two **distinct, bot-manageable** roles: a restrictive quarantine role and a verified role. Configure server channel/role permission overwrites so quarantined members cannot reach normal channels; assigning a role alone **does not** restrict access. Run `/setup`, `/module enable verification`, `/verification verified-role`, `/verification quarantine-role`, `/verification channel`, then `/verification enable` and `/verification panel`. The bot must outrank both roles and have Manage Roles. Use `/verification mode` for `BUTTON`, `MANUAL`, or `BUTTON_AND_ACCOUNT_AGE`; set `/verification min-account-age` (e.g. `7d`) **before** selecting the age-gated mode, or switch to another mode before clearing the age requirement. `/verification rules-ack` configures acknowledgement before button verification. `/verification status` inspects settings; `/verification status target:<user>` inspects a member. MODERATOR or higher can use `/verification approve` and `/verification reject`; rejection leaves the member restricted and **never** bans automatically. Configuration/panel commands require internal ADMIN. A posted panel uses persistent button IDs and PostgreSQL member state; only the current configured panel is accepted. A young/unknown-age account remains pending for staff review when age gating is enabled. Staff can approve it explicitly.

## V2 anti-raid

First enable `verification` as a module and configure its quarantine role. Set `/config set security_log_channel` and enable `logging`, or set `/antiraid config field:alert_channel value:<channel-id>` to a dedicated channel; at least one configured destination is required before `/antiraid enable`. Then run `/module enable antiraid` and `/antiraid enable`. `/antiraid status` shows state; `/antiraid config` inspects/updates `join_window_seconds`, `join_threshold`, `young_account_age`, `young_account_weight`, message spam counts/window, `mention_threshold`, `auto_quarantine`, and `alert_channel`. ADMIN manages configuration. SENIOR_MODERATOR or higher uses `/antiraid emergency action:enable|disable` with an optional reason. Manual or automatic emergency mode persists until a staff member explicitly disables it; all new joins require manual verification review and are quarantined where configured. Join bursts, young-account weight, message-frequency and mass-mention metadata are deterministic signals. A single young account alone does not start emergency mode. Responses restrict/quarantine and alert staff for review, never automatically mass-ban or permanently ban. Message content is not requested, stored or scored; repeated links cannot be detected without Message Content intent. Join audit rows retain only IDs, timestamps, age and short signals and are pruned after 30 days (on subsequent joins and hourly maintenance). Message counters are process-local and reset on restart. Configure a dedicated alert channel or the existing security log channel and verify the bot can send embeds. If Discord roles, permissions, logging destinations or API calls fail, review the internal warnings and fix server configuration promptly.

## V3 role menus

Enable `roles` after `/setup`. Internal ADMIN can `/role-menu create name kind exclusive max`, `/role-menu add-option id role label [description] [required-role] [forbidden-role]`, `/role-menu remove-option`, `/role-menu edit id [name] [exclusive] [max] [enabled]`, `/role-menu list`, `/role-menu publish id channel`, or `/role-menu delete id`. Add/remove options before publishing; select menus support up to 25 options and button menus up to 12 roles (separate Add and Remove controls). An exclusive menu allows at most one role at a time; nonexclusive menus enforce `max` across menu options. Configuration is in PostgreSQL and published message/channel IDs persist across restarts. Buttons use stable explicit add/remove actions so repeated delivery does not toggle roles; select controls reconcile the selected set. Deleted channels/messages and stale controls fail safely; repairing an inaccessible panel requires an administrator to recreate it. Menu grants refuse missing, managed, dangerous Discord-permission and internal permission-mapped roles and roles at/above the bot's hierarchy; the bot needs Manage Roles, a higher role than every offered role, and permission to post in the destination. Membership restrictions are checked on role additions. Never use a self-role menu to grant staff powers.

## V3 tickets

After `/setup`, set `/config set ticket_category <category-id>`, enable `tickets`, then `/ticket config staff-role:<role> [max-active:<1–10>]`. The category must be in the guild; the staff role must be a dedicated non-`@everyone`, non-Administrator role for trusted support staff. Discord members with Administrator can bypass channel overwrites regardless of ticket configuration. The bot needs Manage Channels, Manage Roles, View Channel, Send Messages and Read Message History. `/ticket open type:<SUPPORT|REPORT|APPEAL|PARTNERSHIP|BUG_REPORT|OTHER>` creates a dedicated **private text channel** (not a thread): `@everyone` is denied View Channel, and only the creator, configured staff role and bot are explicitly allowed. The bot records an opening placeholder before Discord creation and uses PostgreSQL locking for duplicate/capacity checks; failures are logged and handled as reconciliation work rather than silently treated as success. Channels are not permission-synced to a public category.

The creator can `/ticket status`, `/ticket list`, and close their own ticket; internal HELPER can `/ticket claim`, `/ticket add`, `/ticket remove`, and `/ticket list all:true`; MODERATOR can `/ticket transfer` and close another member's ticket; ADMIN configures tickets. `/ticket close id [reason]` captures only that channel's conversation and attachment URLs into a human-readable transcript in PostgreSQL before deleting/archiving the channel. `/ticket transcript id` is MODERATOR-only and returns the retained record as private 7 MiB UTF-8-safe attachment parts; transcripts are **not** posted to a public log or transcript channel. Claim/transfer are atomic conditional state changes; duplicate close must not produce multiple persisted transcripts. A failed transcript fetch leaves the channel for retry; a failed Discord cleanup after DB closure needs staff reconciliation. Ticket text is fetched at close, not globally archived. Transcripts, report details and appeals contain sensitive data: restrict database backups and personnel access, define a retention/deletion policy, and do not publish transcripts. The optional transcript-channel setting is not an automatic posting destination.

## V3 reports and appeals

Enable `reports`; no moderation or tickets dependency is required. Members use `/report submit category description [user] [evidence_url]` and `/appeal submit reason [case_id]` privately. An optional case must belong to this guild and target the appellant; no other case history or moderator notes are exposed. Internal MODERATOR can `/report list|view` and `/appeal list|view`; SENIOR_MODERATOR can `/report close id note` and `/appeal review id decision:<ACCEPTED|REJECTED> note`. Responses are ephemeral, sensitive report/appeal text stays out of normal log channels, and audit notifications include only record IDs/status. Reports impose a persistent one-hour per-reporter cooldown; appeals impose a one-day per-appellant cooldown and a single pending appeal. Staff decisions record the outcome without automatically punishing or reversing anyone.

## V3 suggestions

After `/setup`, enable `suggestions` and set `/suggestion config channel:<text-channel>` as internal ADMIN; the bot needs View Channel, Send Messages and Embed Links there. Members `/suggest content:<text>` and use persistent Upvote/Downvote buttons. One vote per user per suggestion is enforced by a PostgreSQL primary key; repeating the same vote is a no-op, and changing direction atomically switches it. Bots cannot vote. Internal MODERATOR can `/suggestion status id status:<PENDING|UNDER_REVIEW|ACCEPTED|REJECTED|IMPLEMENTED>` and `/suggestion respond id response`; `/suggestion view id` reads the record. Counts are computed from database votes, not embed text. A failed post is retained as a pending record with an explicit reconciliation notice, while deleted/stale posts reject votes; Discord message refresh failures are logged for repair. Suggestion text and official responses appear in the configured **public** suggestions channel, unlike private reports/tickets. Vote rows store only suggestion/user IDs, choice and timestamps. Module gating applies to both commands and vote buttons.

## V4 levels

After `/setup`, `/module enable levels` activates message XP and `/rank [user]`, `/leaderboard` (top ten). Internal ADMIN can use `/levels status`, `/levels config cooldown-seconds xp-per-message min-length level-up-channel|clear-level-up-channel`, `/levels reward add|remove|list`, and `/levels ignore-channel|allow-channel`. Defaults: 10 XP per qualifying message, 60-second per-member cooldown, and a 12-character minimum **only when content is actually available**. Bots, system/webhook messages and ignored channels never earn XP. When content is available, short, command-like and repeated-last-content messages are excluded; a short SHA-256 fingerprint of the last awarded text may be stored, **never full message text for XP**. Message Content intent is **not enabled or required**: for most guild messages, content is unavailable, so the short/command/duplicate-content filters cannot operate; durable per-user cooldown, event-time ordering, last awarded message ID, real-user and channel filters remain active. This is a deliberately limited metadata-only fallback, not equivalent content-based anti-spam. Enable/configure the privileged intent only after a separate privacy review if stronger filters are needed. No V4 voice XP is implemented (it needs durable session eligibility accounting).

Level `n` begins at cumulative `100 × n²` XP, computed by the centralized integer formula; e.g. levels 1/2/3 start at 100/400/900 XP. `/rank` and `/profile` display progress within the current level interval. PostgreSQL serializes each member's awards across processes and persists last-award metadata through restarts; SQL indexes provide deterministic XP-descending/user-ID-ascending ranking without reading all members. XP is committed before optional role/announcement delivery. Configure a reward with `/levels reward add`; each guild/level/role is unique. Configuration and award-time checks reject missing, managed, uneditable, privileged, hierarchy-blocked or internal staff-mapped roles. The bot needs Manage Roles and a higher role than every reward; failures are reported through optional V1 security logging, never undo earned XP. After a Discord outage, staff may need to reconcile already-earned roles manually. Configure a level-up text channel only if the bot can View/Send there; ordinary XP awards never flood staff logs.

## V4 reputation

`/module enable reputation` enables `/rep member:<user>` for internal MEMBER and `/reputation status|config` for internal ADMIN. A successful grant adds exactly +1 public social reputation; it confers **no** moderation permission. Self-grants, bot givers/recipients, non-members and accounts under one hour old are rejected. Defaults are one grant per giver every 24 hours and a stronger seven-day cooldown for the same recipient. Configurable global cooldown is 60–604800 seconds; same-target cooldown must be at least global and at most 2592000 seconds. History and aggregates persist in PostgreSQL, and a transaction-scoped lock serializes one giver's concurrent attempts across processes and restarts. History stores only guild/giver/receiver IDs, a nullable Discord interaction ID for durable replay idempotency, and timestamps; cooldown rejection reports remaining seconds. A delayed replay of the same successful interaction never grants a second point even after cooldown expiry. Extra accounts can still circumvent some social limits: this is not an identity verification or staff-trust system.

## V4 starboard

After `/setup` and `/module enable starboard`, internal ADMIN sets `/starboard channel`, optionally `/starboard threshold` (1–25; default 5), `/starboard emoji` (default ⭐), `/starboard self-star`, `/starboard ignore-channel|allow-channel`, then `/starboard enable`. `/starboard status` shows settings; `/starboard disable` withdraws existing mirrors and stops further publication; re-enabling requires fresh eligible reaction activity. The bot needs GuildMessageReactions intent, View Channel/Read Message History in source channels and View Channel/Send Messages/Embed Links/Read Message History in the destination. It fetches all reaction-user pages and counts distinct non-bot users, excluding the source author unless self-stars are allowed; duplicate gateway events and concurrent crossings are serialized against the persisted source→post mapping. The configured emoji, threshold, channel exclusions and settings are guild-specific. Ignoring a source channel withdraws already mirrored posts before the command completes, serialized against in-flight publication; moving the configured board attempts to migrate existing posts. Sources invisible to `@everyone` are never mirrored. An NSFW source is never mirrored into an SFW destination; source visibility/NSFW changes and an NSFW destination becoming SFW trigger channel-update reconciliation that withdraws newly incompatible mirrors. When count falls below threshold or a source message/channel is deleted, its mirrored post is removed (and the mapping marked removed/deleted). A deleted starboard post is recreated on subsequent reconciliation. Failed Discord operations leave state available for retry; if an orphan cleanup fails, inspect sanitized operational errors and IDs.

Starboard posts show author, source channel, timestamp, star count and a jump link; text appears **only if Discord supplied it**. Without privileged Message Content intent, text is normally unavailable, but links/counting still work. No message text is stored in the starboard database. Source and destination visibility should still be reviewed by guild administrators: mirroring deliberately republishes messages from public channels. Do not use the starboard for restricted/private channels.

## V4 member profiles

`/module enable profiles` exposes `/profile [user]` as a read-only public facade. It shows available joined date, display name and any enabled levels (XP, progress, rank, XP-worthy message count) or reputation score; disabled source modules are omitted without making profiles fail. `/rank` and `/leaderboard` require `levels` to be enabled separately. The profile never reads or reveals moderation notes, reports, appeal text, ticket transcripts or staff-only information; it invents no achievements/voice history. The bot needs access to guild-member lookup for commands but does not require the privileged member-event intent just for `/profile`.

## V5 community events

Enable `events` after `/setup`. HELPER+ uses `/event create title start channel [description] [end] [capacity]`; the creator can edit/start/close/cancel their own event, and internal MODERATOR can manage any event. Members use `/event view|list|join|leave` or persistent Join/Leave buttons. An RSVP is **not** attendance: `/event attendance id user` explicitly marks an RSVP after the event starts. The creator does not occupy a slot unless they join. Capacity checks and status transitions lock PostgreSQL rows, so final-slot joins and repeated button deliveries are safe. Status is SCHEDULED, ACTIVE, COMPLETED or CANCELLED; end time is optional. Titles and descriptions have 256/2000-character limits.

Supply strict ISO-8601 dates with explicit `Z` or numeric offset (for example `2030-06-01T18:00:00+07:00`); ambiguous local dates are rejected even if guild `/config timezone` is set. Absolute `timestamptz` values are stored; Discord `<t:...>` renders each viewer's local time. The guild timezone does not silently reinterpret command input. Durable 24h/1h/10m reminders and start/completion transitions are checked by the shared scheduler after restarts. Already-past reminder offsets are skipped. Failed or deleted announcements and stale edits/RSVP counts are retried from persisted pending presentation state (bounded scheduler/backoff). Announcement embeds/RSVPs are public; event titles and descriptions are deliberately retained. The bot needs View Channel, Send Messages, Embed Links and Read Message History. Discord reminder sends cannot be made atomic with a PostgreSQL commit; an outage in the send/receipt boundary may need staff inspection (see `V5-VALIDATION.md`).

## V5 giveaways

Enable `giveaways`. MODERATOR+ uses `/giveaway create prize duration_minutes winners channel` and `/giveaway end|reroll|cancel`; members use `/giveaway view` and Enter/Leave buttons. Optional role, account age, guild age, verified membership and minimum level restrictions are checked on entry **and again when drawing**. Verification/levels must be enabled before requiring them; disabling a source does not silently qualify entrants. Up to 300 unique entrants per giveaway are supported. A row-locked draw uses Node cryptographic randomness to choose distinct currently eligible entries (fewer eligible members means fewer winners). An original end is idempotent; each `/giveaway reroll` deliberately records a new historical draw, excludes all prior winners, and reports no eligible winners when none remain. Result notices and missing or externally deleted ACTIVE announcement posts are reconciled on subsequent bounded scheduler runs, including after restart; a replacement has a new message ID and old buttons are rejected. ENDED/CANCELLED posts are not recreated, and deletion never invalidates a committed draw. If Discord accepts a send but its receipt is lost, staff may need to inspect ambiguous notifications. A deleted original post does not roll back the draw. The bot needs View Channel, Send Messages, Embed Links and Read Message History, not Manage Events or Administrator. Prize and eligibility are public, while entrant/winner IDs remain persisted.

## V5 temporary voice

Enable `tempvoice`; internal ADMIN configures `/tempvoice setup lobby category [limit] [private]`, `/tempvoice status|disable`. A member entering the configured voice lobby receives a private/manageable room with a persistent one-active-owner reservation; repeated voice events reuse rather than duplicate the room. An owner in their own ACTIVE room can `/voice rename|lock|unlock|limit|kick|allow|deny|transfer|status`, affecting only that room, never guild roles or moderation authority. Transfer requires another human occupant. Names are at most 100 characters and limits are 0–99. Empty rooms are marked in PostgreSQL and cleaned after a one-minute grace period with bounded due batches, restart reconciliation and a chance to rejoin. Occupancy uses cached voice states and targeted member lookups rather than the privileged bulk Guild Members intent. Definite pre-create validation/API rejections release reservations; ambiguous creation outcomes retain a logged reservation for manual reconciliation. External voice joins and database transactions are not one atomic system; orphan cleanup failures require operational review. The bot needs View Channel, Manage Channels, Manage Roles (for permission overwrites), Move Members and Connect. `/voice lock` denies default joins while individually allowed members remain exceptions; Administrator and pre-existing role overwrites may bypass a channel lock; verify guild role permissions. No voice-duration measurements or voice-time achievements exist.

## V5 achievements

Enable `achievements` independently; `/achievements [user]` displays public cosmetic milestones for first XP-worthy message, 100 XP-worthy messages, level 5/10, first/ten reputation points, first event RSVP, **confirmed** attendance and first giveaway win. Stable IDs are versioned in code and uniqueness in PostgreSQL prevents replayed or concurrent awards. Source hooks run only after domain state commits; viewing a member lazily evaluates thresholds already satisfied without running a full-guild startup backfill. Disabled source modules are neither queried nor presented, with no hard dependency on them. Only public community IDs and award times persist; achievements confer no staff powers and never expose private notes, reports or tickets. Voice-time achievements are not implemented; analytics aggregates do not award achievements.

## V5 scheduler and migration

Events, giveaways and empty-room cleanup share a bounded 30-second polling wakeup. PostgreSQL is authoritative for claims, uniqueness and future-state transitions; no action depends solely on a long in-memory timer. This is not a generic automation engine. Migrate additive V5 `drizzle/0006_shallow_excalibur.sql`, `drizzle/0007_easy_maestro.sql` and `drizzle/0008_blue_dreadnoughts.sql` before starting new code; leave applied V0–V4 migrations unchanged. V5 stores explicit event text, prizes and ordinary community IDs, never chat transcripts, voice audio or private staff material.

## V6 guild analytics

After `/setup`, analytics is disabled by default. Internal ADMIN can use `/analytics enable|disable|config retention_days:<30–730>`; HELPER+ can use `/analytics status|summary range:<24h|7d|30d|90d> [timezone:<IANA>]`. Default retention is 180 days, configurable per guild from 30 to 730 days; bounded maintenance prunes hourly aggregates and stale member state, while message/command replay-deduplication keys expire after 72 hours. Disabling analytics stops new event collection; do not interpret retained historical data as current activity. UTC-hour buckets and absolute time ranges avoid DST double counting; summaries group those immutable buckets into guild-local days using the configured IANA timezone without rebucketing stored history.

**Actually collected:** counts of non-bot/non-system/non-webhook message creations and top channel IDs; observed human member join/leave transitions and net growth (plus current Discord member count where available); observed human voice seconds by guild/channel (excluding AFK); guild slash-command invocations, failures and accumulated execution duration; and bounded summaries of existing moderation cases, tickets, suggestions, events, confirmed attendance, giveaways, entries/winners, member levels/reputation and achievement records. These business figures are read from existing domain tables rather than duplicated telemetry. **Not collected:** message text, edits/deletes as activity, attachments, voice audio, voice XP, unique-active-user analytics, historical membership before enablement, comprehensive Discord-wide activity or exact offline voice presence. Message Content intent remains **OFF**; no content is required for analytics. Message/command IDs are stored temporarily for deduplication, member IDs for lifecycle state and voice IDs/channel IDs for active sessions and short-lived disconnected-user fences (pruned after 72 hours); aggregates are hourly, not per-message archives.

Member join/leave events require both Server Members (`GuildMembers`) intent enabled in the Discord Portal and `ENABLE_GUILD_MEMBERS_INTENT=true`; without them, member-join analytics is incomplete, and the separate logging/verification/antiraid intent requirements still apply. Repeated same-state events do not create new transitions; a first observed leave does not prove an earlier observed join. Voice-state updates and bounded cache-based live-session heartbeats measure observed intervals, using targeted member fetch when a voice-state member is not cached; failed classification leaves the snapshot incomplete and does not delete persisted sessions. An interval over ten minutes since the last observation is treated as a stale gap, **not** credited as participation. Startup/re-enable reconciliation requires a complete per-guild snapshot before normal accrual; intervening gateway events create no-credit baselines. Snapshot cutoffs and durable PostgreSQL observation-sequence boundaries precede Discord observation; gateway events reserve no-credit pending state before slow identity lookups, so delayed finalization cannot be erased by a snapshot. PostgreSQL locks/conditional writes preserve newer events, module toggles use a monotonic database epoch, and bounded disconnected-session tombstones prevent stale snapshots from reviving a leave. Bot downtime and disabled intervals are not credited; restarts, gateway gaps, incomplete caches or heartbeat limits can undercount voice duration. Do not use these approximate totals for billing or disciplinary decisions.

## V6 opt-in dashboard

The dashboard is **off by default** (`DASHBOARD_ENABLED=false`) and shares the bot process/database. To enable it, set `DASHBOARD_ENABLED=true`, `DASHBOARD_HOST` (default `127.0.0.1`), `DASHBOARD_PORT` (default `3000`), `DASHBOARD_BASE_URL` (required canonical public origin), `DASHBOARD_SESSION_SECRET` (required, at least 32 characters), and `DISCORD_CLIENT_SECRET` (required Discord application OAuth client secret). `DASHBOARD_TRUST_PROXY` defaults to `false`; enable it only behind a trusted reverse proxy that overwrites forwarded headers and terminates TLS. Generate a long random session secret **privately** with a cryptographic generator (for example `node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"` in a private terminal); store it only in your uncommitted `.env`/secret store, never paste it into issues or logs. Do not reuse the bot token or client secret as the session secret. Existing `DISCORD_CLIENT_ID` supplies the OAuth application ID.

For local development, use `DASHBOARD_BASE_URL=http://127.0.0.1:3000`, keep the default loopback host/port, register exactly `http://127.0.0.1:3000/auth/callback` in the Discord Developer Portal, then open `http://127.0.0.1:3000/login` after starting the bot. In general register `${DASHBOARD_BASE_URL}/auth/callback` (without a trailing slash in the base URL); OAuth scopes are `identify guilds`, not `bot` or Administrator. Non-loopback use requires an HTTPS base URL and TLS/reverse-proxy deployment; never expose the plain HTTP listener publicly. Trust proxy headers only from your controlled proxy, restrict direct listener access, and configure the proxy's host/scheme/forwarded headers consistently with the canonical origin.

The OAuth guild list is only a discovery snapshot: every guild page/action freshly fetches the guild, member and roles, then applies Eiren's internal role mappings; a guild-role/member fetch failure denies access. Guild owner has owner authority; Discord's Administrator permission alone is **not** mapped to bot ADMIN. Dashboard access begins at HELPER, with page/action-specific higher levels (including owner-only permission-role changes). OAuth access tokens are used only to fetch identity/guild IDs during sign-in and then discarded. Sessions persist only a SHA-256 hash of their random cookie token in PostgreSQL, expire after 24 hours idle or 30 days absolute, and can be revoked on logout; cookies are HttpOnly/SameSite=Lax and Secure with the `__Host-` prefix for HTTPS (loopback HTTP uses non-Secure host-only cookies). OAuth discovery is capped at 200 guild IDs per session to bound current-membership checks. Mutations require a session-derived HMAC CSRF token plus an exact canonical Origin, are rate-limited, and record only guild/actor/action/target identifiers, success flag, request ID and timestamp as audit metadata, **not** request payloads or OAuth tokens. Audit persistence occurs after a domain mutation; on audit failure check state before retrying.

Available read views: guild overview, recent moderation cases/reports metadata and authorized case detail, on-demand REST-verified member lookup (identity, level, reputation and earned achievements), role menus and permission mappings, ticket metadata (not transcripts), suggestion status/votes, levels/rewards/leaderboard, events, giveaways, analytics summary (24h/7d/30d/90d), and bot settings. Analytics and other module-gated views depend on enabled modules. Accessible HTML forms invoke the existing domain services for module toggle, guild timezone, moderation warn, ticket close, suggestion status, levels minimum length, event cancel, giveaway end, analytics toggle/retention, and owner-only role mapping set/remove; each POST rechecks authorization, module state, CSRF, canonical Origin and destructive confirmation. Other domain operations remain slash-command-only; no dashboard transcript viewer, message-content archive, broad moderation console or arbitrary bot automation is implemented.

## Development checks

`pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm db:check`. With PostgreSQL running, run `pnpm db:migrate`, `pnpm db:smoke`, `pnpm db:v4` and `pnpm db:v5`; the V5 workflow uses isolated synthetic guilds and cleans their records. For V6 database checks run `pnpm db:v6` with PostgreSQL available; `pnpm dashboard:check` briefly starts an unauthenticated loopback server with synthetic OAuth dependencies, checks DB/health/login/CSS/redirect/headers, then shuts it down. See `V6-VALIDATION.md` for separate evidence categories. `pnpm db:generate` creates additive SQL plus Drizzle journal/snapshot after schema changes; never edit already-applied migrations.

## Layout

- `src/app`: startup, registration, migration entry points, dependency assembly, module registry
- `src/core`: environment, database, logger, errors, permission, command/event dispatch
- `src/modules/core`, `moderation`, `logging`, `verification`, `antiraid`, `roles`, `tickets`, `reports`, `suggestions`, `levels`, `reputation`, `starboard`, `profiles`, `events`, `giveaways`, `tempvoice`, `achievements`: independent feature definitions and services
- `src/services`: reusable guild configuration and module behavior
- `src/repositories`: Drizzle-backed persistence
- `drizzle`: versioned SQL migration and migration metadata

## Current limitations

No AI/automation, Redis, or multi-language responses. Message logs contain identifiers, not contents. Staff notes are stored in PostgreSQL and visible only to authorized moderation commands. V3 report/appeal descriptions, ticket transcripts and suggestions remain in PostgreSQL until deleted through an administrator-approved retention process; no automatic V3 retention job is provided. Ticket transcripts are accessible through a private staff-only command and database backups, not public logs. Discord-client user-account automation is not included; human-operated component responses must be verified separately. See the validation documents for environment-specific gaps.
