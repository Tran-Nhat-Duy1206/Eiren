# V8 design proposal — Data Stewardship & Operational Confidence

**Status:** design only; not approved for implementation. **Reviewed baseline:** `main` at `0a25461f26951659d41ee00dbe8a3bb472962ee4` (V7 merged; migrations `0000`–`0017`). This document proposes future work; it does not change runtime behavior, migrations, dependencies or README. The V7 gate recorded 445/445 automated tests, 69/69 V6 and 189/189 V7 PostgreSQL checks, and 11/11 dashboard smoke checks; those are historical evidence, not newly rerun V8 checks (`V7-VALIDATION.md`).

## 1. Executive summary

**Recommend V8: Data Stewardship & Operational Confidence.** First establish a defensible policy for retained private V3 material and a way to verify/recover bot operations, then provide narrowly authorized retention/redaction and metadata-only operations visibility. Add a repeatable CI/restore gate. This closes concrete, documented gaps before adding more content-bearing modules or a large dashboard CRUD surface. No observed defect requires reopening the completed V7 merge; these are important next-release and eventual production-readiness gaps, not claims of a newly discovered V7 release blocker.

Keep the single Node process and PostgreSQL transaction/lease model. Redis, an event bus, a separate worker or dashboard process, and Message Content intent have no demonstrated need. AI remains **frozen**: production constructs `new AiRuntime(ai, null)` (`src/app/main.ts`); this roadmap contains no provider, inference, AI dashboard, AI actions or AI-led features. Existing Automation is operational V7: scheduled `STATIC_MESSAGE`/`STAFF_LOG`, ADMIN-controlled, with manual `UNCERTAIN` reconciliation; do not build a parallel announcements engine (`README.md:134-140`).

## 3. Concrete debt, severity and security posture

**BLOCKER for any future claim of automated compliant deletion or production-grade recovery, not a retroactive V7 merge blocker:** there is no agreed owner/subject-deletion authority, legal-hold rule or deletion protocol for private ticket/report/appeal text and backups. Claiming those guarantees without policy and verification would be false (`README.md:155-157`, `src/core/database/schema.ts:206-274`). There is likewise no restore rehearsal from a usable backup; do not claim a recovery point or time until measured.

**IMPORTANT for V8:** (1) closed V3 transcripts, descriptions/evidence and staff notes have no scheduled retention; dashboard audit metadata is also indefinite; (2) `/healthz` returns `{status:'ok'}` regardless of DB/gateway/scheduler readiness (`src/dashboard/web.ts:121`); (3) the sequential 30-second V5 scheduler records sanitized failure logs but no queryable last-success/last-error/lag state (`src/app/v5-scheduler.ts:8-40`); (4) Discord writes and PostgreSQL cannot commit atomically, so V3/V5 orphan/ambiguous work and Automation uncertainty need visibility rather than blind retries (`V3-VALIDATION.md:21-26`, `V5-VALIDATION.md:20-24`, `V7-VALIDATION.md:68-72`); (5) no GitHub Actions CI/migration-with-PostgreSQL gate; startup table probes do not substitute for documented migration-before-start plus a restore drill (`src/app/main.ts:270-331`, `README.md:9-19`). Audit writes occur after dashboard mutations; an audit failure can leave an already-committed action and is logged rather than retried (`src/dashboard/web.ts:103,235-265`). Surface that degraded state without replaying a mutation.

**OPTIONAL / only with user evidence:** richer role-menu or giveaway dashboard editors, generic aggregate metrics, abstracting repeated service shapes, additional long-running workers and lint/format tooling. Do not call existing bounded PostgreSQL patterns “debt” merely because they are not distributed.

Already present security controls matter: dashboard requests use OAuth sessions with hashed DB token storage, fresh guild/member/role checks and Eiren permission levels, bounded forms/rate limits, CSRF tokens plus canonical Origin, CSP/no-store and safe error responses (`src/dashboard/web.ts:19-24,101-120,235-265`, `src/dashboard/access`, `src/dashboard/auth`). Role-map mutations are owner-only and reject dangerous roles (`src/dashboard/web.ts:85-95`); static Automation reauthorizes a live human and validates channels before dispatch. Scope the V8 review to new read/deletion routes, audit failure and sensitive-content leakage; do **not** rebuild V6/V7 auth or relax Discord permission/hierarchy checks. Never put message bodies, notes, report text, database SQL or tokens in health responses, operational logs or audit rows. Environment validation and HTTPS/cookie/reverse-proxy requirements are already partly enforced (`src/core/config/env.ts`, `README.md:116-122`); a deployed TLS proxy/process-manager configuration has not been validated here.

## 4. Privacy and data governance inventory

“Current deletion” below refers to an exposed authorized workflow, not a DBA's ability to issue SQL. Most guild-owned tables cascade on deletion of the entire guild row, but **that is not** a safe, exposed guild-admin deletion or per-user erasure API. User IDs are not user-FK-linked; a blanket SQL delete misses related rows. Discord posts and database backups are separate copies and will not be erased by database retention.

| Data and sensitivity | Retention/automatic cleanup today | Exposed deletion and integrity consideration |
| --- | --- | --- |
| Ticket transcript, attachment URLs, creator/participants, close reason (**high/private**) | No ticket/history TTL, including CLOSED; transcript text stored in `tickets.transcript` (`schema.ts:206-235`, `V3-VALIDATION.md:23-24`). | Staff-only ephemeral download; no ADMIN delete/purge or subject erasure. Child participants cascade if parent deleted; preserve ticket lifecycle/counts when redacting transcript, and consider already-sent Discord transcript copies/backups. |
| Reports and appeals (**high/private**) | Description, evidence URL, resolution note, appeal reason/review note stored indefinitely (`schema.ts:237-274`). | Review commands, no exposed deletion. Appeal `case_id` FK uses SET NULL when case deleted; deleting cases would lose accountability and break pending-appeal semantics. Cooldown and open-review rows must not be pruned. |
| Moderation cases and staff notes (**high/accountability**) | Case reason/target/moderator/status and note text persist; punishment expiry changes state, **not** retention (`schema.ts:45-66,152-162`). | No routine user/admin erasure. Preserve active/pending cases and a defensible audit trail; design separate authorized note-content redaction and reviewed legal/security holds, never casual case hard-delete. |
| Suggestions and votes (**public text + personal IDs**) | Content, staff response and vote/user IDs persist (`schema.ts:281-309`). | No exposed delete; deleting parent cascades votes. | Dashboard sessions and audit (**identity/access metadata**) | Hashed session tokens expire at idle/absolute bounds and cleanup runs on scheduler; audit actor/action/target/request IDs has **no** TTL (`schema.ts:663-688`, `src/app/main.ts:226-233`). | Logout revokes own session; no per-user audit erasure/UI or audit browser. | Analytics (**low-content but member/voice IDs**) | Aggregate buckets guild-configured 30–730 days (default 180), dedupe 72h and bounded member/voice cleanup (`src/modules/analytics/repository.ts:270-287`). | ADMIN dashboard retention setting exists. ### Proposed policy and deletion architecture (conditional on V8 approval)

1. **Define purposes/authority first:** inventory controller/guild-admin scope and verified user-request route, domain-specific lawful holds, backup retention, who may redact and what “deleted” promises mean. This is engineering design, not a legal-compliance certification. Do not give ordinary staff raw archive access; require live Eiren ADMIN for guild policy/deletion, with stronger review for moderation/evidence and a documented off-platform subject-request identity check.
2. **Separate payload from proof:** for CLOSED tickets, retain status/IDs/time and redact `transcript`/attachment URLs after a chosen policy; for reports `CLOSED` at `closed_at` and appeals `ACCEPTED`/`REJECTED` at `reviewed_at`, redact narrative/evidence/review text only after eligibility review, preserving minimal status/provenance. Staff notes/case reasons require independent, stricter review rather than automatic case destruction. Keep an append-only *metadata-only* deletion/audit receipt (actor, guild, domain, record reference, policy version, count, timestamp; no removed content or raw user text). Where NOT NULL text columns exist, a future migration must define safe redacted sentinel/state rather than ad hoc empty strings.
3. **Default conservatively:** candidate opt-in per-guild policy for existing data, explicitly confirmed before first destructive pass; proposed selectable windows after ticket `CLOSED` at `closed_at`: transcripts 30–365 days; after report `CLOSED` at `closed_at` or appeal `ACCEPTED`/`REJECTED` at `reviewed_at`: narrative 90–730 days, subject to product/legal decision. New guild defaults and staff-note rules remain open decisions; until approved, current records are unchanged. Do not silently backdate/prune pre-existing material when a default changes. Exceptions: active/pending cases/appeals, open tickets/reports, holds, live giveaways/events, rate/cooldown/replay windows, outstanding AI reservations and all unresolved Automation `UNCERTAIN` evidence.
4. **Bound and prove every deletion:** indexed eligibility by guild/status/closed-at; small per-tick transactions with `FOR UPDATE SKIP LOCKED`/equivalent guarded ownership and deterministic FK-aware ordering, idempotent redaction, tenant fencing and a dry-run count. Coordinate against concurrent reopen/review/close; test cancellation, failure and restart. Prefer redaction over parent deletion where FKs, historical results or audit would be lost. Test bounded backlog progress and avoid unbounded scans or Discord API calls within pruning transactions.
5. **Subject requests:** inventory all user IDs by guild; distinguish eligible votes/RSVP/profile state from moderation accountability, other people's reports and active anti-abuse keys. Support reviewed, scoped erase/anonymize where technically and policy-wise appropriate, with an explicit unable-to-delete/hold explanation; do not promise one-click global disappearance or delete other people's evidence. Database redaction cannot retract message copies, local exports or old backups; bound encrypted backup lifetime separately and describe restore-time reapplication of deletion decisions.

## 5. Operations, recovery and dashboard findings

The startup lifecycle probes many schema tables before gateway login, registers handlers, starts moderation/V5/analytics/anti-raid/AI/Automation work on gateway readiness, and shuts down client/dashboard/pool (`src/app/lifecycle.ts`, `src/app/main.ts:195-399`). A single V5 scheduler sequentially runs due jobs every ~30 seconds, skips overlapping ticks and logs fixed stage/error type on failure (`src/app/v5-scheduler.ts:8-40`); PostgreSQL rows/locks own due work. Anti-raid, analytics, auth-session, AI metadata and Automation already have bounded maintenance. This is a good base, not a reason to add a queue. The latest V7 validation invoked the installed graceful handler via in-process `process.emit('SIGINT')`, observed `Shutdown complete` and a freed port; it did **not** prove native Windows console-signal delivery (`V7-VALIDATION.md:121`).

**A future ADMIN-only operations page would materially help.** Proposed guild-scoped read model: module enabled/disabled/epoch; last attempted/succeeded maintenance stage and timestamp, fixed error category and stale interval; bounded per-guild pending/failed/oldest ages for scheduled events/giveaway presentation, ticket close/orphan warnings where durable evidence exists, tempvoice unresolved reservation states, and Automation `PENDING`/`RUNNING`/`UNCERTAIN` counts with a link to the *existing* guarded reconciliation view. A small global process panel can show gateway state, lightweight timed PostgreSQL connectivity, startup reconciliation status, running schema/migration version and audit-write degradation. If failures currently exist only in logs, first model them honestly as “not tracked”, not zero. Never expose other guilds' counts or raw errors. In-memory last-success is process-lifetime only; if restart history is a requirement, design minimal durable sanitized checkpoint metadata, not a full job queue.

Keep cheap anonymous `/healthz` **liveness**; add a distinct bounded readiness contract before advertising DB/gateway/scheduler as healthy, with `503` for an unavailable dependency, safe fixed statuses, timeout/caching and no secrets or private counts. A database outage may prevent rendering the authenticated page: readiness must degrade safely and operators need out-of-band logs. Do not use a readiness probe to auto-trigger a migration or a Discord write. Categorize backlog counters as actionable vs ambiguous; never add “retry all”. Existing Automation ADMIN sent/not-sent reconciliation stays human-evidence-based and at-most-once. Prioritized later safe-repair investigations: ticket closed-channel cleanup; giveaway announcement/result receipts; unresolved tempvoice creation; event presentation; moderation expiry; stale voice sessions. Read-only metadata first, then only separately reviewed domain-specific repairs with preconditions and audit.

### Dashboard coverage and highest-value gaps

`src/dashboard/web.ts:21-24,46-98` and `src/dashboard/data/dashboard-read-service.ts:23-109` show actual authorization/pages. **A = meaningful manage:** core module toggle, timezone and owner role mapping; moderation WARN; ticket CLOSE; suggestion status; levels min length; event CANCEL; giveaway END; analytics toggle/retention; Automation ADMIN rule CRUD/enable/disable/manual reconcile. **B = read-only/limited:** overview, member lookup, moderation cases and report metadata, ticket metadata (no transcript), suggestion/vote summary, role menus, levels/leaderboard, event/giveaway metadata, analytics summary, verification/anti-raid/ticket settings. **C = slash-command-only for remaining workflows:** verification/anti-raid configuration/emergency, logging channels, role-menu publishing, report/appeal staff review, private notes/full moderation, ticket claim/transcript/participant management, suggestion staff response, XP rewards, reputation, starboard, profiles, tempvoice, achievements and AI status/explicit input. **D = not represented as dedicated dashboard workflow:** operations/readiness/maintenance/audit investigation, consent-based retention/deletion, reconciliation for V3/V5, backups; logging/reputation/starboard/tempvoice/achievements have no dedicated management page. A module may be C and D in different respects; this is not a request to port every command.

Ranked missing workflows: (1) retention policy/eligible-content redaction and safe preview (high privacy value, high authorization risk); (2) operations/backlog and existing Automation uncertain evidence (high operator value, metadata-only if carefully scoped); (3) reports/appeals staff review **only after** strict privacy/access model (high value, high content exposure risk); (4) ticket repair and giveaway/tempvoice ambiguous cleanup (high value but dangerous side effects, read-only first); (5) verification/anti-raid configuration (useful but error-prone role/overwrite preflight); (6) role-menu/event/giveaway creation (convenience, already workable via slash). Keep private transcripts out of the dashboard unless a separate threat model and consent approve it.

### Backup, deployment and CI boundary

`README.md:9-19,116-122,142-144` documents manual `db:migrate` before start, local Compose and HTTPS/canonical URL/cookie/proxy requirements; `src/core/config/env.ts` validates environment. There is no evidence of hosted deployment, configured restart policy, reverse-proxy TLS test, secret-management service, production monitoring, scheduled backups or restore drills. **Production requirements when deployed:** least-privilege DB role; tested backup schedule, encryption/ACL and expiry; pre-deploy versioned backup plus forward-only migration review and rollback-by-code/fix-forward plan; stop/upgrade/start order with `db:migrate` before new bot; manager restart policy; proxy/TLS and trusted-proxy/cookie validation; gateway/DB readiness monitored; structured sanitized logs retained per policy. `pnpm dev`, guild-scoped command registration, local Compose and loopback smoke are development conveniences, not deployed proof. The bot should **not** store DB passwords or upload dumps.

Provide an operator-owned `pg_dump`/`pg_restore` checklist using environment/secret-manager credentials **outside the repository**, restrict file permissions, encrypt/store off-host, verify migration journal and counts on an isolated disposable restore, prohibit production Discord credentials/outbound sends during rehearsal, and dispose of plaintext fixtures. Periodically re-run the restore, record measured recovery point/time, apply outstanding erasure ledger before serving a restored DB, and document missing credentials/Discord permission recovery. Code can test migrations and detect health; backup transport/rotation and disaster recovery remain runbook/host responsibilities absent a real deployment.

**CI belongs in V8.** Add a GitHub Actions design for pinned Node 24/pnpm 10, dependency cache and PostgreSQL service; run `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm db:check`, migrate a fresh disposable DB, `pnpm db:smoke`, `pnpm db:v4`, `pnpm db:v5`, `pnpm db:v6`, `pnpm db:v7`, and `pnpm dashboard:check` with synthetic OAuth/placeholder Discord values. Require careful script/env review, no real bot token, AI key, Discord sends or cross-test DB collision; include a migration-upgrade rehearsal fixture where needed. CI does not replace bounded live Discord/human OAuth checks. Branch protection with required checks becomes useful **after** CI exists and is reliable; no need to invent lint/format gates or add dependencies without demonstrated payoff. V0–V7 ledgers remain trustworthy historical manual evidence, not an existing CI system.

## 9. Non-negotiable security, privacy and scale constraints

- Eiren ADMIN is required for guild retention controls and operations diagnostics; separately verify Discord guild membership and live internal permission on every request, not just OAuth guild-list cache. Stronger authorization/hold review is needed for notes and disputes. Tenant-scope every query and receipt, limit/paginate, avoid actor/user IDs where an aggregate suffices.
- Public health reveals no secrets or guild data; ADMIN diagnostics reveal only status/count/oldest age/timestamp/fixed error code. **Never** show token, connection URL, SQL, raw exceptions, message bodies, transcripts, report/appeal text, private notes or configured Automation action text.
- Message Content remains OFF. V8 A, B, D and E need no additional privileged intents. Only C's join/leave welcome requires the already optional privileged GuildMembers intent; keyword FAQ/custom listeners would require privileged Message Content and are explicitly rejected.
- No separate Redis, distributed lock, worker or event bus now: existing PostgreSQL locks, claims, dedupe and 30-second bounded single-process ticks fit observed workload (`src/app/v5-scheduler.ts`, `V7-VALIDATION.md:68-72`). Revisit only after measured throughput, recovery-lag or HA requirements; readiness/backup gaps are not fixed by adding infrastructure.
- Maintain explicit backups and restore-time erasure replay; retention controls only the primary DB. A live deletion operation must not advertise deletion from historic encrypted backups or Discord posts that it did not actually remove.

## 10. Open product decisions before V8 approval

1. Which guild/admin role may set policy or approve subject requests, who authorizes a hold, and what audit metadata lifetime is defensible? Is owner co-approval required for case/note redaction?
2. Are opt-in existing-guild policies and proposed 30–365-day closed-ticket / 90–730-day closed-report/reviewed-appeal windows acceptable? What are the exact defaults for new guilds, notice/hold exceptions and local legal obligations?
3. What is the precise treatment of public suggestion posts/votes and Discord-delivered transcripts when database text is redacted? Which operations are explicitly **DB-only**?
4. What deployment (if any), backup storage/operator, RPO/RTO, TLS proxy and monitored readiness consumer actually exist? Who owns restoring a DB and replaying prior deletions?
5. Which one ambiguous V3/V5 recovery case has sufficient durable evidence to support a safe guided repair? If none, keep V8.5 strictly observational.
6. Is there demonstrated bilingual guild demand for English/Vietnamese across bot and dashboard, and which locale wins between interaction and guild preference? Reassess as a separate future version rather than silently expanding V8.

**Decision checkpoint:** approve/change this design and the policy decisions before implementation. Until then, `README.md`, migrations, dependencies, intents and runtime remain at V7.
