## Scheduler maintenance incident (2026-09-27 UTC)

A bounded pre-fix bot run reached **Dashboard listening on 127.0.0.1:3000** and **Discord gateway ready**, then emitted `job="analytics"`, `errorType="Error"`, `msg="V5 scheduled reconciliation failed"` on its first scheduled pass; the process was stopped. Directly invoking real PostgreSQL `analytics.runDue()` with a one-row-per-table cap isolated **`analytics_guild_hourly`** (SQLSTATE **42883**, `timestamp with time zone < interval`), before session cleanup or guild voice work. The retention SQL passed `now` as an untyped PostgreSQL parameter in timestamp-minus-interval expressions. PostgreSQL inferred an interval for the parameter, producing an invalid comparison with the `timestamptz` bucket column. The same defect affected the three hourly tables, member-state expiry and active-voice expiry; the first failing SQL was guild-hourly because the job processes tables sequentially. All three `now` expressions now explicitly cast to `timestamptz`. The existing per-guild `COALESCE` retention fallback was preserved. No development data was deleted to mask the fault.

Scheduler errors now report a fixed, sanitized stage and the version-neutral **Scheduled reconciliation failed** message, without SQL, error messages, environment values, tokens or cookies. Analytics success is logged only at debug level with the job name. Unit coverage checks staged, secret-free logging; `pnpm db:v6` executes the real six-table cleanup in a rollback-only fixture and checks zero-expired, live and expired dashboard sessions. Direct database checks found zero existing dashboard sessions, passed all three `cleanupExpired` cases, and confirmed development-guild analytics is disabled; scheduled voice work therefore skips that guild. A live voice snapshot with participants was not attempted.

## Final-review voice accounting races and correction

The adversarial V6 review found two blocking interleavings even though the earlier 280 tests passed:

1. **Quick-restart downtime:** A gateway event could call `voice()` before asynchronous startup reconciliation finished. A persisted `updated_at` less than ten minutes old was then charged through process downtime. Per-guild readiness now starts false; early verified events persist only no-credit gateway baselines/tombstones, while unclassified gateway events fence the user without claiming human participation. An incomplete or failed snapshot leaves readiness false; the bounded scheduler retries. A successful complete snapshot establishes a fresh no-credit baseline before normal accounting. The first post-recovery interval additionally checks the baseline time, including a same-millisecond cutoff collision. Analytics disable/re-enable (slash, generic module controls or dashboard) invalidates readiness via the shared module service. No disabled interval is later charged.
2. **Stale snapshot overwrite/delete/resurrection:** Startup or heartbeat previously took its timestamp *after* asynchronous snapshot collection; snapshot writes using `updated_at <= timestamp` could replace a later move, delete a later join or resurrect a later leave. Startup and scheduler now capture the cutoff *before* collection; the snapshot freezes channel IDs before awaited member lookups. Reconciliation/heartbeat use a single PostgreSQL guild advisory transaction, strict `updated_at < cutoff` writes/deletion guards, and nullable disconnected-user tombstones to protect later leaves (additive migration `drizzle/0011_fuzzy_skaar.sql`). New/uncertain channels establish a baseline at snapshot completion instead of backdating participation. Voice events, snapshots and analytics module toggles use the same guild lock; database module-state checks reject a delayed write after disable. A monotonic `guild_modules.version` (additive `drizzle/0012_brainy_stick.sql`) fences even a disable/re-enable occurring within the same millisecond, independently of wall-clock comparisons. Tombstones expire under the existing bounded 72-hour voice-state cleanup. No raw voice history or voice XP was added.

Focused unit tests first reproduced pre-ready accrual on the original code, then exercised startup retries, central toggle invalidation, immutable snapshots and unknown-member fencing. The required full suite passed once after the code fix: `pnpm typecheck`, `pnpm test` (**285/285 in 38 files**), `pnpm build`, `pnpm db:check`, `pnpm db:migrate`, `pnpm db:smoke`, `pnpm db:v6`, and `pnpm dashboard:check` (all local HTTP checks true on an ephemeral loopback port). Real PostgreSQL `pnpm db:v6` reports **48 assertions** against synthetic guild records: short/long restart downtime, a fresh normal interval, stale move/join/leave preservation, a heartbeat racing a newer move, identical timestamp boundaries, re-enable without an intervening event, duplicate/reordered updates, same-millisecond module epochs, and delayed writes after module toggles. Its synthetic records are removed, and the existing rollback-only retention fixture remains intact. A separate bounded run of the rebuilt `pnpm start` with process-local debug logging showed **Discord gateway ready**, **dashboard listening on 127.0.0.1:3000**, explicit **voice analytics startup reconciliation complete**, and an initial analytics scheduler pass plus **at least two approximately 30-second periodic ticks** without errors; the process was stopped afterward and port 3000 had zero listeners. ## Delayed gateway finalization versus a committed snapshot

A subsequent adversarial review found the *opposite* commit order missing from the 48 PostgreSQL assertions: a snapshot copies human U in channel A at cutoff T0, pauses on another member's REST lookup; U leaves at T1 and its handler timestamps the leave but stalls before its database write; the snapshot writes A with `updated_at=baselineAt` at T2 > T1; the delayed leave arrives at T3 and the old `at <= updated_at` check drops it. A later rejoin could charge the intervening absence as A. A deterministic, barrier-controlled real-PostgreSQL fixture first failed on `delayedLeaveAfterSnapshotMustDisconnect` with all synthetic data removed, confirming the unpatched bug; sequential event-first regressions did not exercise this order.

**Fix:** additive `drizzle/0013_youthful_tony_stark.sql` adds a per-analytics-module monotonic `voice_sequence` and per-user `observation_seq`, `observation_epoch`, `pending` fields to the existing bounded voice-state rows; no permanent raw event history. The voice gateway path bypasses the generic asynchronous module precheck and reserves a sequence plus a no-credit pending row in a short PostgreSQL guild-then-member locked transaction **before** targeted REST classification. The DB itself checks module enablement. Local ingress reservations are queued in receipt order; the authoritative ordering and epoch checks remain in PostgreSQL. Before reading Discord state, a separate short transaction takes the guild's durable sequence/epoch boundary; no database lock spans REST. Reconciliation and heartbeat cannot alter a same-epoch pending row or a row with an observation sequence newer than their boundary. Finalization only accepts the still-current reservation in the same module epoch, and resets the baseline instead of claiming an uncertain interval; superseded or old-epoch finalizers are rejected. Unknown identities finish as no-credit disconnects, and the existing 72-hour bounded state cleanup removes abandoned reservations/tombstones. Earlier restart, ten-minute stale-gap, AFK/bot, UTC-hour, disable/re-enable and version fencing policies remain intact; short uncertain sessions can be undercounted.

Focused deterministic tests assert reservation precedes a held targeted lookup, bypasses the dispatcher's asynchronous module precheck while retaining the analytics module registry key, and preserves per-guild ingress/DB-boundary order without sleeps. PostgreSQL fixtures exercise delayed leave/move/join finalization after snapshot commit, pending reservations both before and after boundary capture, a leave/rejoin without false seconds, superseded pending leave, reordered older finalizer, old-epoch rejection and a finalized event whose sequence beats a stale snapshot despite an older timestamp. Synthetic guilds are deleted afterward. The complete suite passed: `pnpm typecheck`, `pnpm test` (**288/288 in 38 files**), `pnpm build`, `pnpm db:check`, `pnpm db:migrate` (also safe when repeated), `pnpm db:smoke`, `pnpm db:v6` (**61/61 real PostgreSQL assertions**) and `pnpm dashboard:check` (all loopback HTTP checks true). ## Non-voice analytics opt-out linearization

Final review identified a separate privacy race: `recordMessage`, `recordMember` and `recordCommand` checked `modules.isEnabled` asynchronously, then their repository transactions could persist dedupe keys, member state or hourly metadata *after* a concurrent administrator disabled analytics. The service check was only an optimization and did not protect the write. A deterministic real-PostgreSQL fixture first failed on `disabledAfterMessageCheckRejectsAllTelemetry` after the module check read enabled=true, a barrier held the caller, the analytics disable transaction committed, and the delayed message writer persisted telemetry; all synthetic rows were removed even on failure.

The repository now acquires the **same guild advisory transaction lock** as every analytics module toggle, reads `guild_modules.enabled` and `version` while holding it, rejects disabled/stale-epoch ingestion **before** any dedupe or state insert, and performs the entire accepted message/member/command write in that short transaction. Member ingestion takes the member-specific lock **after** the guild lock, matching voice writers; no lock spans Discord REST or OAuth. All slash, generic and dashboard module toggles converge on this one guild-locked module write. The service captures the module epoch before its asynchronous enabled check and passes it to the repository: if disable/re-enable advances the epoch during a delayed call, the old call cannot be relabeled as current even when analytics is enabled again. The ingestion linearization point is the locked repository enabled/version check; a writer admitted before disable finishes before that disable can commit, while a writer arriving after committed disable is rejected without partial telemetry. Historical aggregates still follow retention; opt-out stops **new** collection, not history deletion. Voice reservation, startup readiness, tombstones and sequence ordering remain unchanged. No migration was necessary: `guild_modules.enabled` and `version` already existed.

Deterministic no-sleep PostgreSQL barriers cover message, member and command writes after a committed disable, including no message/command dedupe, no member state, and unchanged aggregates, plus all three stale calls after disable/re-enable. A focused unit test checks that the pre-check epoch reaches each repository writer. The prior 288 tests/61 assertions above are historical. The opt-out fix's full run passed `pnpm typecheck`, `pnpm test` (**289/289 tests in 38 files**), `pnpm build`, `pnpm db:check`, `pnpm db:migrate`, `pnpm db:smoke`, `pnpm db:v6` (**67/67 real PostgreSQL assertions**) and `pnpm dashboard:check` (all unauthenticated loopback checks true). The synthetic guild fixtures were deleted. A bounded run of the rebuilt `pnpm start` showed **Discord gateway ready**, **dashboard listening on 127.0.0.1:3000**, explicit **voice analytics startup reconciliation complete**, an initial analytics scheduler pass and at least two approximately 30-second later ticks with no errors. The bot was stopped and port 3000 had no listener. The configured guild still had analytics disabled: this does not verify authenticated browser mutation, enabled-guild live snapshot, or live human voice participation.

## Dispatcher-ingress epoch fence (final non-voice correction)

The 289-test/67-assertion opt-out fix above fenced final database writes, but its epoch was captured only **inside** `AnalyticsService`. Message/member events first awaited the generic event-dispatcher module check; slash interactions awaited reply deferral, command gating, member lookup, authorization and execution before entering the telemetry `finally`. An old event could therefore wait before service epoch capture, undergo disable/re-enable, acquire the **new** epoch and be recorded as new work. The previous PostgreSQL fixture paused only *after* service epoch capture and missed this exact ordering. Focused deterministic message/member/command dispatcher tests failed before this correction: message/member dispatch incorrectly called the generic async module precheck, and command dispatch had not reserved before `deferReply`.

**Correction:** an immutable non-voice ingestion token `{guildId, epoch}` is reserved in a separate short PostgreSQL transaction under the existing analytics guild advisory lock and current `guild_modules.enabled/version` check. Analytics message/member gateway handlers bypass *only* their own generic asynchronous dispatcher precheck; after cheap synchronous bot/webhook/guild filters, reservation is their first async operation. Command dispatch reserves optional telemetry immediately after synchronous command/guild identification, **before** `deferReply` or other awaited command work. A reservation error logs only a sanitized warning and never prevents command execution. The final service writers require the original token (or null, which emits no telemetry), never read a fresh epoch, and the existing guild-locked repository transactions recheck enabled **and matching version** before any dedupe, member state or hourly write. No DB lock spans Discord/network work; other modules keep normal dispatcher gating. The token's transaction is the ingress linearization point: if a toggle wins the DB lock first, the reservation observes its committed state; if reservation wins, a later disable or disable/re-enable invalidates final persistence. An event arriving earlier but whose first DB operation loses the lock to a completed re-enable is classified at that *new DB linearization point*, not via a prior stale async enabled decision. Voice's separate sequence and pending-row design was unchanged; existing migrations suffice.

Deterministic dispatcher tests now cover message/member ingress before any generic module check, preservation of their original epoch across a held final writer and synthetic toggle, command reservation before held `deferReply`, optional reservation failure without command failure, and disabled/null tokens. Real PostgreSQL checks obtain actual ingress tokens, then commit disable or disable/re-enable **before** the delayed message/member/command writers; all reject without dedupe/state/hourly side effects. Separate database assertions cover reservation returning null when disabled and the current epoch only after re-enable. Earlier validation totals above remain historical.
